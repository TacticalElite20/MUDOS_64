The preemptive scheduler uses one per-CPU weighted EEVDF-derived scheduler for all System, .MEXE and .ROOT threads. Weight can be set to Weight_Minimum = 100, Weight_Very_Low = 500, Weight_Below_Normal = 750, Weight_Normal = 1000, Weight_Above_Normal = 1250, Weight_Very_High = 1500 and Weight_Maximum = 4000 and is a proportional CPU-service weight rather than the physical request length, while Latency Class is fixed to Latency_Minimum = 1ms, Latency_Short = 2ms, Latency_Normal = 4ms, Latency_Long = 8ms or Latency_Maximum = 24ms and no custom request sizes exist. Each thread has "base_weight", "inherited_weight", "effective_weight", "base_latency_class", "inherited_latency_class" and "effective_latency_class"; UI/user scheduling state changes the base values, mutex priority inheritance changes only the inherited values, "effective_weight = max(base_weight, inherited_weight)" and "effective_latency_class = shortest(base_latency_class, inherited_latency_class)". All threads default to Weight_Normal + Latency_Normal, foreground threads use Weight_Very_High + Latency_Normal, minimized threads use Weight_Very_Low + (unchanged Latency Class), the "System" process its Kernel thread uses Weight_Very_High + Latency_Normal, UI and Compositor use Weight_Very_High + Latency_Short, Audio Engine uses Weight_Normal + Latency_Minimum, Memory Management uses Weight_Normal + Latency_Long, DEDWM uses Weight_Normal + Latency_Short, FACIOS Compressor/Decompressor Thread x uses Weight_Above_Normal + Latency_Maximum and Font Engine uses Weight_Normal + Latency_Short. Thread virtual runtime is updated as "thread->task_virtual_runtime += runtime_ns * Weight_Normal / thread->effective_weight;" and every per-CPU runqueue has its own "virtual_time" which advances while runnable work executes as "runqueue->virtual_time += runtime_ns * Weight_Normal / runqueue->total_runnable_weight;", where Total_Runnable_Weight is the effective Weight of the THREAD_RUNNING thread plus every THREAD_READY thread assigned to that CPU and runnable-set/effective-Weight changes account the previous interval before changing that total. A THREAD_READY thread is EEVDF-eligible when "vruntime_signed_difference(runqueue->virtual_time, thread->task_virtual_runtime) >= 0"; eligibility is not a thread state. If runnable work exists but every READY entity is temporarily ineligible because of rounding/runnable-set changes, virtual_time advances monotonically to the lowest READY task_virtual_runtime so at least one runnable entity becomes eligible instead of idling the CPU. Each scheduling request has "request_size_ns", "request_remaining_ns" and "virtual_deadline"; a new request uses exactly its fixed Latency Class length and "virtual_deadline = task_virtual_runtime + request_size_ns * Weight_Normal / effective_weight". Preemption preserves the unfinished request_remaining_ns and current request deadline. Migration preserves the unfinished request_remaining_ns and normalized service state, then reconstructs task_virtual_runtime and recomputes the current request deadline in the destination runqueue's virtual-time domain. When exactly one thread is runnable on a CPU, request expiration alone does not need to generate a scheduler interrupt; execution is fully accounted for and the request is renewed when another scheduling event/runnable competitor appears. READY threads are stored in a Red-black tree keyed on "virtual_deadline" with PID then TID as deterministic tiebreakers; every queued thread stores "subtree_min_vruntime" so an entire subtree is skipped when its minimum task_virtual_runtime is greater than runqueue.virtual_time, making insertion/removal/earliest-eligible-deadline selection O(log(runnable_count)). Every THREAD_READY thread which is currently ineligible is additionally stored in a second Red-black tree keyed on "task_virtual_runtime" with PID then TID as deterministic tiebreakers using the thread its separate "eligibility_node". The deadline tree remains the authoritative READY runqueue and the eligibility tree is only an auxiliary index for finding the next eligibility crossing. When runqueue.virtual_time reaches or passes the lowest task_virtual_runtime in the eligibility tree, every now-eligible thread is removed from the eligibility tree while remaining in the deadline tree. Whenever a READY thread enters/leaves the runqueue or its task_virtual_runtime changes, its eligibility-tree membership is updated under that runqueue its lock. The earliest ineligible READY thread defines an eligibility-crossing scheduler deadline using "runtime_ns_until_eligibility = ceil((next_task_virtual_runtime - runqueue->virtual_time) * runqueue->total_runnable_weight / Weight_Normal)" based on attributable execution time; runnable-set/effective-Weight changes account the previous interval first and then recalculate this deadline. Because unrelated hard-interrupt time does not advance runqueue.virtual_time, an eligibility-crossing LAPIC deadline may fire early in wall-clock time; the handler accounts actual attributable runtime, makes every thread whose eligibility condition is now true eligible for selection and re-arms the deadline when the crossing has not yet occurred. Eligibility-crossing scheduler deadlines are non-deferrable and receive no timer slack. Priority inheritance propagates both the highest required effective Weight and shortest required Latency Class through mutex-owner chains, is recomputed whenever a waiter is added, removed, terminated or receives ownership and ends when no longer required; propagation is bounded by the process its thread_count and encountering the same owner twice is a process-fatal mutex deadlock. Priority-inheritance propagation never holds more than one mutex "wait_lock" simultaneously. Under the current mutex its "wait_lock" it retains the required thread/mutex references and snapshots the next owner/"blocked_mutex" relationship, releases that "wait_lock", acquires the next mutex its "wait_lock" and revalidates the snapshot; if the relationship changed, propagation/recomputation retries from the changed state before modifying inherited scheduling state. Before changing an effective Weight the current runtime is accounted, normalized service lag is preserved, the new Weight is applied and the current deadline is recomputed without retroactively re-accounting old service. When the effective Latency Class becomes shorter, the current request remaining time is capped to the new class maximum and its deadline is recomputed; when it becomes longer, the active request is never extended and the longer class starts with the next request. Before a thread blocks, runtime is accounted, its current normalized service lag is stored, the unfinished scheduling request is discarded and "blocked_since_time" is recorded. Saved service lag decays linearly toward zero over 64ms of blocking and becomes zero at or after 64ms, then on wake it is reconstructed relative to the destination runqueue.virtual_time and a fresh request is created. Saved/migration service lag is clamped to maximally 16ms service bonus or 16ms service debt. A new thread starts with "task_virtual_runtime = destination_runqueue.virtual_time" and zero service lag. Ordinary runnable-Weight load-balancing migration is allowed when the source logical CPU has more than 1 running-plus-ready thread and has >=20%(5% hysteresis used, arm above 20%, disarm under 15%) more running-plus-ready effective Weight than another logical CPU and uses a 32ms per-thread cooldown. Topology-spread migration is a separate migration trigger from ordinary runnable-Weight load balancing, does not require the source logical CPU to have more than 1 running-plus-ready thread and does not require the ordinary 20% runnable-Weight imbalance threshold, but still uses the same 32ms per-thread migration cooldown. Native Ring-3 TLS/TSS: MUDOS_64 provides kernel-supported thread-local storage (TLS) and thread-specific storage (TSS) for every .MEXE and .ROOT thread. On x86-64, FS is the dedicated Ring-3 TLS register while the kernel reserves GS for kernel/per-CPU use. Every Ring-3 thread receives its own randomized TLS allocation and one user Thread Control Block (TCB); FS.base points at that TCB whenever the thread is running. The main executable its static TLS template is copied once per thread, zero-fills the TLS BSS portion and is aligned exactly as declared by the validated executable header. MUDOS_64 uses an x86-64 Variant-II-style static TLS layout: the TCB is at FS:0 and main-executable static TLS objects use linker-generated negative offsets from FS.base, allowing C "_Thread_local" and compiler TLS references to execute without a syscall on the fast path. The TCB contains only user-space TLS/runtime metadata and is never trusted by Ring 0 for kernel security decisions. The kernel stores the authoritative "user_fs_base" in struct thread, validates that it is a canonical Ring-3 address belonging to that thread its TLS allocation and restores it on every context switch before returning to Ring 3. Ring 3 cannot set FS.base to an arbitrary address through a raw privileged instruction or syscall. CR4.FSGSBASE is not enabled for Ring-3 use in this ABI; the kernel restores IA32_FS_BASE only when the incoming thread its cached user_fs_base differs from the current CPU value, avoiding a redundant MSR write on same-thread continuations while keeping FS authoritative. Existing MEXE_v1.8/ROOT_v1.2 images are accepted as zero-static-TLS images, while MEXE_v1.9/ROOT_v1.3 add validated TLS template offset, initialized TLS size, total TLS size and TLS alignment fields. Newly created threads always receive a fresh copy of the process static TLS template.


Dynamically loaded .MLIB modules use the same native TLS system through a process-local dynamic TLS vector in the TCB. Every loaded module with a TLS template receives a non-zero process-local TLS module generation/index. The first access by a thread lazily allocates and initializes that module its TLS block for that thread; mudos_module_tls_address() validates the module generation and requested offset and returns the calling thread its address. Module unload invalidates its TLS module generation before any storage is released, and stale module/TLS handles are rejected. This keeps static TLS references syscall-free while avoiding a fixed per-thread allocation for every possible dynamically loaded module.


TSS in this section means thread-specific storage and is unrelated to the x86 hardware Task State Segment already used for privilege transitions/TSS.RSP0. TSS is a separate process-local key/value facility intended for runtime-managed thread-specific pointers and does not replace compiler TLS. Each process has at most MUDOS_MAX_TSS_KEYS_PER_PROCESS=128 TSS keys. A TSS key handle contains the slot index in its low 32 bits and a non-zero generation in its high 32 bits; generations increment on destruction and a slot reaching UINT32_MAX is permanently retired rather than wrapping. Each thread lazily allocates its TSS value table on its first TSS set. Every per-thread value slot stores the key generation beside the pointer-sized value, so destroying a key is O(1) and stale values in other threads are ignored without scanning every thread. TSS get/set validates the current process key generation and never allows one process to access another process its TSS. Ring 0 never invokes arbitrary Ring-3 destructor callbacks during forced thread/process cleanup. A C/C++/language runtime that wants TSS destructors executes them in Ring 3 during orderly thread shutdown before mudos_thread_exit(); forced termination simply releases the TSS storage. TLS/TSS storage is released only after the thread can no longer execute and is included in normal process/OOM cleanup.


 The system is UEFI only, x86_64 only, multi-core, single user only. No user system(system boots immediately into the UI and doesn't have a user account login profile or anything like that). All kernel threads run in Ring 0 while all the .MEXE and .ROOT threads run in Ring 3(only the core Ring 3 implementation). C language and Assembly used only. Uses the FreeRTOS philosophy of having the entire system monolithic but internally divided into separately running loops. No init is needed since kernel = init. No behavioral anti-virus scanning is used. Preventive software security consists of Ring 3 separation, separate process address spaces, the three-tier FACIOS permission rule above, ASLR, KASLR, NX on every mapping which is not explicitly executable, strict W^X so no mapping may be writable and executable at the same time, read-only kernel code and read-only kernel constant data after initialization, SMEP and SMAP when supported, one non-present guard page below every kernel and Ring 3 stack, stack canaries for kernel and Ring 3 stacks, checked user-copy helpers which validate the complete user range and use STAC/CLAC only around the exact copy when SMAP is active, checked integer addition/multiplication for sizes, offsets and allocation calculations and strict executable-header, section-range, entry-point and permission validation before any .MEXE or .ROOT image is mapped. Memory allocator: Type: Four-Level Paged Virtual Memory Management, Physical Layer Allocator: Fixed-Size Buddy Page Allocator + Slab Allocator, Virtual Layer Allocator: Hardware-Enforced Page Isolation via MMU, Granularity: 4 KiB Fixed-Size Framing. Memory uses ASLR. The buddy allocator manages orders 0(1 page, 4 KiB) through 11(2048 pages, 8 MiB) using one intrusive doubly linked free list per order: "struct buddy_freelist    
{    
    uint64_t head;

};    




struct buddy_free_node    
{    
    uint64_t previous;

};    




struct buddy_allocator    
{

};". Physical memory is divided into one or more aligned buddy arenas constructed only from valid UEFI usable-memory ranges, one "struct buddy_allocator" is used per arena and blocks are never merged across arena boundaries. Each buddy arena therefore has its own lock and allocations/frees affecting different arenas may proceed independently; there is no global buddy lock. Each free block stores its node in its first page, while the compact physical-page metadata below stores its free flag and order. Allocation rounds N pages upward, removes one block from the lowest available sufficient order and splits downward; freeing computes "buddy_page = arena_base_page + ((block_page - arena_base_page) XOR (1ULL << order))" and merges upward only while the resulting buddy lies inside the same arena and the buddy metadata says it is free at the same order. Buddy membership and free-list insertion/removal are O(1), so allocation and free perform at most 12 split/merge steps. Allocation uses the current CPU its bucket and therefore does not contend with slab allocation on another CPU. Every slab page records its owning CPU; an object freed on another CPU is placed onto that owner CPU its atomic remote-free list and incorporated into the applicable local bucket before its next allocation/refill operation, so cross-CPU frees do not require a global slab lock. Each bucket keeps separate partial, full and empty page lists. Allocation takes the first partial page, or moves the first empty/new page to the partial list, so selecting a page with free objects is O(1); pages move between the lists whenever "free_objects" changes. Allocations above 2048 bytes reserve a virtually contiguous address range and are backed by one or more buddy-allocated physical blocks. Each physical buddy block is at most order 11, while larger virtual allocations are assembled from multiple physical blocks and mapped contiguously in virtual memory. The allocator prefers the largest suitable available orders and uses smaller orders for the remainder. Each process strictly has its own "PML4 > PDPT > PD > PT" for strict process isolation. PID 0 uses PCID 0 on every logical CPU. Every logical CPU independently owns a 4096-entry hardware-PCID cache; PCID 0 is reserved for PID 0 and local PCIDs 1 through 4095 are dynamically bound to Ring 3 process identities. Each local slot records PID, process instance ID, a non-zero monotonically increasing 64-bit pcid_generation assigned through that CPU its local next_pcid_generation and the last tlb_generation observed for the bound process, while each process stores one CPU-indexed process_pcid_binding containing the last PCID/pcid_generation assigned to it on that CPU so the binding can be validated in O(1). A local PCID may be rebound while its former process is still alive because PCID identity is CPU-local; rebinding first invalidates that hardware PCID on that CPU with INVPCID single-context before the new binding becomes usable, and different CPUs may use the same numeric hardware PCID for different process identities simultaneously. Every process owns a monotonically increasing tlb_generation which changes whenever a page-table modification requires cached translations to become stale. Each logical CPU uses its local PCID-slot metadata to retain valid translations across ordinary process switches while guaranteeing that rebound or modified address spaces are invalidated before Ring 3 execution. Local pcid_generation or process tlb_generation wrap causes "RING 0 EXECUTION ERROR" instead of wrapping. If all non-zero local PCID slots are occupied, that CPU evicts and safely rebinds one local cached slot instead of rejecting process or thread creation. The thread states THREAD_RUNNING(when a program is currently running on the CPU), THREAD_READY(when a program is currently ready to be run on the CPU but another thread is currently running its turn), THREAD_MIGRATING(only a THREAD_READY thread may enter this state; a selected THREAD_RUNNING thread is first preempted and changed to THREAD_READY, then changed to THREAD_MIGRATING after it is no longer executing, transferred to the destination logical CPU's runqueue and changed back to THREAD_READY; "pre_migration_state" is therefore THREAD_READY, while THREAD_DEAD has priority over migration), THREAD_BLOCKED(THREAD_BLOCKED means that the thread is waiting for an event and is not eligible for scheduling, block_reason identifies the waiting condition, sleeping threads use THREAD_BLOCK_SLEEP, mutex waiters use THREAD_BLOCK_MUTEX, IPC waiters use THREAD_BLOCK_IPC, storage/filesystem I/O waiters use THREAD_BLOCK_IO, manual-reset event waiters use THREAD_BLOCK_EVENT, thread-termination waiters use THREAD_BLOCK_THREAD, UI-event waiters use THREAD_BLOCK_UI, audio waiters use THREAD_BLOCK_AUDIO, network waiters use THREAD_BLOCK_NETWORK and GPU fence/swapchain waiters use THREAD_BLOCK_GPU) and THREAD_DEAD(when a thread gets thread state THREAD_DEAD its TID and thread instance ID are removed from the active thread table once no references to that thread remain, its PID remains active while its owning process remains PROCESS_ALIVE or PROCESS_EXITING, the PID and process instance ID are removed from the active process table only after the process reaches PROCESS_DEAD and no references to that process remain) are implemented. The scheduler won't run threads with the thread state THREAD_BLOCKED. Because the kernel is tickless, each CPU programs its LAPIC in TSC-deadline mode for the nearest applicable deadline: the current THREAD_RUNNING thread's EEVDF Latency Class request exhaustion when another runnable competitor exists, the earliest currently ineligible THREAD_READY thread's EEVDF eligibility crossing, the earliest local THREAD_BLOCK_SLEEP wakeup, migration cooldown expiry, or background maintenance deadlines. THREAD_BLOCK_SLEEP threads are stored in a per-CPU deadline min-heap where earliest wakeup is O(1) and insertion/removal are O(log(n)); every other THREAD_BLOCK_* waiter remains only in the blocking queue or wait object owned by its corresponding subsystem. When the deadline fires, the current thread's attributable runtime is accounted exactly once, all expired deadlines are processed, every ineligible READY thread whose task_virtual_runtime is now <= runqueue.virtual_time is removed from the auxiliary eligibility tree and becomes eligible for normal selection, an exhausted request is renewed and normal earliest-eligible-virtual-deadline selection is performed, and the LAPIC deadline is re-armed. EEVDF request exhaustion, EEVDF eligibility crossings and scheduler-correctness deadlines are non-deferrable. The invariant TSC is used as the primary high-resolution monotonic clock only after cross-CPU TSC synchronization is measured and validated during CPU bring-up. Every online CPU records a signed TSC offset relative to CPU 0 using repeated bounded synchronization measurements; if the raw TSCs are not sufficiently synchronized, MUDOS_64 applies the recorded per-CPU offset whenever converting a local TSC value into the global monotonic time domain. If a stable bounded offset cannot be established, HPET or ACPI PM Timer is used as the monotonic clocksource instead. LAPIC TSC-deadline mode still uses each local CPU its raw hardware TSC, with a global absolute deadline converted through that CPU its recorded TSC offset before IA32_TSC_DEADLINE is programmed. LAPIC timer operation is initialized using TSC-based calibration derived from CPUID 0x15, with HPET, ACPI PM Timer, or PIT as fallback calibration sources. Deferrable timer deadlines may fire up to 0.1ms late for non-minimized tasks and up to 2.0ms late for minimized tasks. This reduces interrupt overhead by coalescing nearby timer events, conceptually similar to Linux timer slack. CPUs without runnable work enter HLT idle until their next deadline or an external interrupt makes work available. MUDOS_64 uses a native stateful IPv4 firewall integrated directly into Drivers.c between validated IPv4 packet processing and TCP/UDP endpoint delivery on receive, and before final packet transmission on send. The firewall uses default-allow outbound policy and default-deny unsolicited inbound policy. Inbound packets which belong to an already established/expected TCP connection or to a valid reply flow created by permitted outbound UDP traffic are allowed, while a new unsolicited inbound TCP/UDP flow is dropped unless it targets a locally listening endpoint which application/system policy explicitly permits or matches an explicit allow rule. Invalid packet state is dropped before endpoint delivery. Firewall matching uses direction, protocol, local/remote IPv4 address and local/remote port where applicable. Firewall rules are stored as an immutable generation-swapped ruleset for read-mostly packet processing: packet-processing CPUs read the current published generation without one global firewall lock, while a rule update builds and validates a complete replacement ruleset and atomically publishes it. Existing packet processing either sees the complete old generation or the complete new generation, never a partially modified rule table. Stateful flow entries are sharded by the same flow ownership used by per-CPU networking so ordinary connection-state updates do not require one global firewall-state lock. The firewall never trusts Ring 3 packet metadata to bypass filtering, and ordinary .MEXE programs cannot disable or bypass it.

Networking packet processing is per-CPU. For each active network interface, MUDOS_64 creates up to one receive queue and one transmit queue per logical CPU when the NIC and interrupt resources support enough independent hardware queues. RSS or the NIC's equivalent receive-flow hashing is used when available so packets belonging to the same IPv4 TCP/UDP flow are directed to the same logical CPU, and MSI-X queue interrupts are given affinity to their corresponding logical CPU where interrupt-routing hardware permits this. When fewer hardware queues than logical CPUs are available, logical CPUs are deterministically distributed across the available queues; when the NIC provides only one receive queue, the receive interrupt performs only bounded validation/enqueue work and software flow hashing distributes later protocol processing across the per-CPU network workers. Every TCP/UDP flow has one current owner logical CPU selected from a stable hash of protocol, local/remote IPv4 address and local/remote port. All ordering-sensitive protocol state for that flow is processed by its owner CPU, preserving packet ordering and avoiding concurrent modification of one connection by multiple CPUs. Each logical CPU owns its local receive-work queue, transmit-work queue, timer/protocol work, flow-state shards and packet-buffer caches, stored in cache-line-separated per-CPU state. Fast-path receive/transmit processing therefore does not use one global network lock. A thread running on a non-owner CPU may submit work to the flow owner through a bounded cross-CPU queue; the submitting CPU does not directly mutate the remote flow state. Network work is interrupt-driven/event-driven rather than continuously polled, and THREAD_BLOCK_NETWORK remains the blocking state for application threads waiting for DNS/TCP/UDP progress.

Scalable network fan-in allows network work produced concurrently by multiple logical CPUs to converge on one TCP listener, UDP endpoint, process/network wait object or application receive path without serializing the complete network stack behind one global lock. Each fan-in target owns bounded per-CPU producer queues plus an atomic pending-source bitmap and one coalesced readiness state. A producer CPU publishes completed receive/accept/error/readiness state into only its own producer queue, then atomically sets its source bit; only the transition from no pending readiness to pending readiness needs to trigger the applicable waiter wakeup, so many packets or connections arriving concurrently do not generate redundant scheduler wakeups. The consuming thread/network path atomically snapshots and clears pending source bits, drains the indicated producer queues in deterministic source-CPU order, merges their events into the endpoint's normal TCP/UDP receive or accept ordering rules and rechecks the pending-source bitmap before sleeping again. A producer which publishes after the consumer's final empty observation sets its bit and performs the normal wake path, preventing lost wakeups. TCP byte-stream ordering is never reconstructed by arrival CPU: all packets for one TCP flow are first serialized by that flow's owner CPU, while fan-in combines already ordered per-flow results. UDP datagrams remain individually atomic and retain their source address/port metadata. Fan-in queue overflow applies protocol-correct bounded backpressure/drop behavior rather than overwriting unread entries, and all queue indices/generations use non-wrapping or explicit wrap-safe arithmetic. This design permits receive processing, firewalling, TCP/UDP flow work and endpoint delivery to scale across logical CPUs while keeping a single application-visible network handle and the existing native network ABI unchanged. Every process has "spinlock_t mutex_table_lock;" and "struct process_mutex_slot mutex_slots[MUDOS_MAX_MUTEXES_PER_PROCESS];", where each slot contains a mutex pointer, a 32-bit generation and a retired flag. Mutex handles are local to the creating process. The lower 32 bits contain the table index, the upper 32 bits contain the generation and handle 0 is always invalid. Generations start at 1; an invalidated slot increments its generation, while a slot invalidated at "UINT32_MAX" is permanently retired instead of wrapping. A handle is valid only when the process is PROCESS_ALIVE, its index is in range, the slot is live and not retired and the generations match. Invalid, stale, destroyed, foreign or otherwise inconsistent handles are considered program-fatal misuse and terminate the calling process. The mutex object stores its exact owner process PID/process instance ID and exact owner TID/thread instance ID so reused identifiers cannot impersonate old objects or owners. Each occupied mutex-table slot owns one mutex reference, each successfully resolved operation temporarily owns one reference and each queued waiter owns one thread reference plus one mutex reference. Reference count 0 or overflow while acquiring, or underflow while releasing, is a Ring 0 execution error. A mutex is deallocated only when its table ownership, temporary operations and queued-waiter references are all gone. Handle resolution validates the slot while holding "mutex_table_lock" and acquires its temporary object reference before releasing that lock, preventing deallocation between validation and operation. Creation allocates and initializes a mutex with one table-owned reference, publishes it only while the process remains PROCESS_ALIVE and returns MUDOS_MUTEX_INVALID when allocation fails or no usable slot exists. Mutexes are non-recursive and use a strict FIFO wait queue through "wait_head", "wait_tail" and the thread its separate "mutex_wait_next" pointer, so the process thread list, scheduler runqueue, mutex queue and IPC wait queue never share one linkage field. Locking an unlocked mutex records the current thread as owner. Locking a mutex already owned by the calling thread terminates the process. Locking a mutex owned by another thread enqueues the caller in O(1), gives the queue its required references, records "blocked_mutex", updates and propagates priority inheritance before the owner can continue running, releases the temporary syscall reference and atomically changes the caller from THREAD_RUNNING to THREAD_BLOCKED with THREAD_BLOCK_MUTEX through "scheduler_block_current_and_unlock()". That scheduler operation is called while "wait_lock" is held, removes the thread from runnable eligibility under its runqueue lock, releases "wait_lock" only at the scheduler-defined safe point and switches context. It returns only after ownership has been transferred to that thread, its block metadata has been cleared, it has become THREAD_READY and the scheduler later runs it again. Unlocking is valid only for the exact owner thread. When waiters exist, ownership is transferred directly to the oldest valid FIFO waiter while the mutex remains locked, that waiter changes from THREAD_BLOCKED/THREAD_BLOCK_MUTEX to THREAD_READY through "scheduler_wake_thread()" and its former queue-owned references are released only after runqueue ownership is established. This direct handoff prevents another thread from acquiring the mutex between unlock and wake-up. When no waiter exists, owner becomes THREAD_HANDLE_NONE and "locked" becomes 0. After every waiter insertion, removal, termination, ownership transfer or unlock, the affected owner threads recompute "inherited_weight" from the highest effective waiter Weight and "inherited_latency_class" from the shortest effective waiter Latency Class on every mutex they currently own, with temporary mutex references and the existing mutex-table/wait-lock rules used so no object can disappear during the recomputation. Priority-inheritance propagation never holds more than one mutex "wait_lock" simultaneously: the current mutex its owner/blocked relationship and required retained references are captured under that mutex its "wait_lock", that lock is released before the next mutex its "wait_lock" is acquired, and the captured relationship is revalidated after the next lock is acquired; if it changed, recomputation retries from the changed state. Every normal read or modification of "locked", "destroying", "owner", "wait_head", "wait_tail" and queued "mutex_wait_next" is protected by that mutex its "wait_lock"; "locked" therefore does not need to be atomic. Attempting to unlock without exact ownership terminates the process. Destroying a mutex succeeds only when it belongs to the calling PROCESS_ALIVE process, is not already being destroyed, is unlocked, has no owner and has no waiters. Destruction first marks the object as destroying under "wait_lock", then validates and invalidates its table slot under "mutex_table_lock", drops the former table-owned reference and finally drops the operation reference. Operations which resolved the handle immediately before destruction may still hold temporary references, but after acquiring "wait_lock" they detect "destroying", release their references and terminate without modifying the mutex. Destroying a locked, owned, contended, stale, foreign or already-destroying mutex is program-fatal misuse. THREAD_BLOCKED threads are never schedulable. THREAD_BLOCK_SLEEP is owned by the sleep subsystem and may only be awakened when the current monotonic time has reached or passed "sleep_deadline"; THREAD_BLOCK_MUTEX is owned by the corresponding mutex queue and is never awakened by the sleep subsystem; THREAD_BLOCK_IPC is owned by the corresponding process IPC queue and is awakened only after a message is published to that queue or during process termination; THREAD_BLOCK_IO is owned by the applicable storage/filesystem I/O completion object; THREAD_BLOCK_EVENT is owned by the applicable manual-reset event wait queue; THREAD_BLOCK_THREAD is owned by the target thread's termination-wait structure; THREAD_BLOCK_UI is owned by the applicable window/UI event queue; THREAD_BLOCK_AUDIO is owned by the applicable audio-stream wait structure; THREAD_BLOCK_NETWORK is owned by the applicable network/DNS/TCP/UDP wait structure; THREAD_BLOCK_GPU is owned by the applicable GPU fence/submission/swapchain wait structure; THREAD_BLOCK_PROCESS is owned by the target process completion object; THREAD_BLOCK_PIPE is owned by the applicable byte-stream endpoint wait queue; THREAD_BLOCK_WAIT_MANY is owned by exactly one wait_context spanning its registered waitable objects; and THREAD_BLOCK_COMPLETION is owned by the applicable completion queue. Each blocking subsystem publishes the completed/satisfied/failed wait state before calling scheduler_wake_thread(), and only the subsystem owning the current block_reason or process-termination cleanup may clear that blocking ownership and make the thread THREAD_READY. The current CPU its "runqueue_lock" owns runnable membership and transitions among THREAD_RUNNING, THREAD_READY and THREAD_MIGRATING. A mutex block path holds "wait_lock" before acquiring the runqueue lock, while a mutex wake path holds "wait_lock", validates and clears the mutex-block metadata, transfers ownership and then acquires the destination runqueue lock to publish THREAD_READY. No concurrent read or modification of thread "state", "block_reason", "blocked_mutex", "mutex_wait_next" or "ipc_wait_next" is allowed without the lock owning that thread its current scheduler or blocking structure, except after complete detachment under exclusive cleanup ownership. "termination_pending" remains atomic. Process state is independent from thread state. A process remains PROCESS_ALIVE while its threads may be THREAD_RUNNING, THREAD_READY or THREAD_BLOCKED. If the main thread exits, a process-fatal error occurs or a thread exits while owning a mutex, the process changes to PROCESS_EXITING and later PROCESS_DEAD after cleanup. Process termination atomically sets every thread its "termination_pending", prevents new syscalls and waits for running kernel operations to finish or reach a defined safe termination point. While holding "mutex_table_lock", cleanup changes PROCESS_ALIVE to PROCESS_EXITING, detaches and generation-invalidates every occupied mutex slot and transfers each former table-owned reference to cleanup, so no mutex can subsequently be created or newly resolved. It then releases "mutex_table_lock" before processing each detached mutex separately under that mutex its "wait_lock": "destroying" is set, the FIFO is detached, every valid blocked waiter is marked for termination, removed from mutex blocking and changed to THREAD_DEAD under the locks owning its state, ownership is cleared and the lock is released. Cleanup then releases every detached waiter its queue-owned thread and mutex references and finally the detached table-owned reference. All process threads are removed from runqueues and blocking structures, including IPC wait queues, process-completion wait queues, pipe wait queues, completion wait queues and wait-many registrations; all mutex queues are empty and no thread remains executing before cleanup releases pipe endpoint references, completion queues, shared-page references, TSS tables, dynamic-module references/TLS blocks, file-backed mappings and the remaining address-space resources and the process becomes PROCESS_DEAD. This prevents permanent blocking, stale ownership, stale handles, leaked references and use-after-free. Every Ring-3 process also owns one reference-counted process_completion object created before the process is published. The object records the exact PID/process instance ID, parent PID/parent instance ID, a completion flag, int64_t exit_status, uint32_t exit_reason, a wait_sequence and a FIFO process-waiter list protected by its own spinlock. Explicit mudos_process_exit(code) publishes that exact code with MUDOS_EXIT_NORMAL. If the main thread terminates through mudos_thread_exit(code), that code becomes the process exit status. User close, mudos_process_kill(), process-fatal API misuse, unrecoverable Ring-3 memory faults and OOM victim termination publish distinct exit_reason values; when no application-supplied status exists, exit_status is 0 and the reason carries the termination cause rather than overloading arbitrary negative status values. The process completion is published exactly once after no new Ring-3 execution/syscalls can begin but before the final process object/resources become unreachable; exit status/reason are written before the completion flag with release ordering and every process waiter is then awakened.


A direct child process completion is retained independently of the active PID table until its parent successfully collects it with mudos_process_wait() or the parent itself terminates. Therefore a child may reach PROCESS_DEAD, leave the active process table and allow its numeric PID to be reused while the old {pid,instance_id} completion remains safely waitable. Completion records are keyed by the complete process handle so PID reuse cannot impersonate the dead child. The parent owns at most 1024 uncollected child-completion records; creation of another child is rejected before publication when that bound cannot be satisfied. A successful parent mudos_process_wait() copies the immutable exit information and consumes the parent completion reference exactly once. Timeout or interruption does not consume it. .MEXE callers may wait only for direct children they own completion rights for, while ROOT/system-management code may wait for another live process when explicitly authorized and retains a temporary completion reference before it can race with death. Parent termination drops all uncollected child-completion references. Process waiters block with THREAD_BLOCK_PROCESS and the same publication-before-wake rule as every other blocking subsystem. Process completion readiness is also exposed to mudos_wait_many(); wait-many observes but does not consume the completion, after which mudos_process_wait(...,0,...) can collect it.


Mutex locking is forbidden in interrupt context because it may block and context switch; spinlocks are used for interrupt-context and other non-sleeping kernel synchronization. The global mutex/scheduler lock order is strictly mutex "wait_lock" first, then the lower-numbered "runqueue_lock" and then the higher-numbered "runqueue_lock". No path may acquire a mutex "wait_lock" while holding a runqueue lock. Priority-inheritance propagation may never hold more than one mutex "wait_lock" at once. "mutex_table_lock" is never held while acquiring any mutex "wait_lock"; creation, resolution, destruction, priority-inheritance recomputation and process cleanup release the table lock before locking an individual mutex. Process cleanup retains detached table-owned references until each mutex has been safely cleaned. These rules prevent deadlocks among mutex-table operations, mutex blocking/waking/destruction, priority inheritance, process cleanup, migration and scheduler runqueues. File-backed Ring-3 mappings: MUDOS_64 natively maps ordinary VFS files into a process address space through generation-safe file-backed mapping objects. A mapping retains the exact validated VFS entry/file-data lifetime required for its semantics, not merely a raw entry ID, and all offset+size arithmetic is checked before any page-table change. File offsets must be 4 KiB aligned; the requested mapping size may end inside the final page and is internally page-rounded, with bytes beyond the mapped logical file range never exposing stale physical memory. The requested [offset, offset+size) range must lie completely inside the file size visible at mapping creation; file mappings do not implicitly extend files, so callers extend/truncate the file explicitly before mapping a larger shared range. Mapping placement uses the same randomized Ring-3 virtual-address allocator as anonymous memory unless a future explicit fixed-address ABI is added. All mapped pages are user pages, obey NX and strict W^X, and may never become writable+executable simultaneously.


MUDOS_FILE_MAP_PRIVATE creates a private snapshot-style mapping. The mapping retains the exact immutable file-data generation visible when the mapping is created. Clean pages are faulted in lazily from that retained file-data version and may be discarded under memory pressure and reconstructed from the same version. Writable private pages use copy-on-write and become anonymous-derived pages after their first write; they never modify the file. Later VFS replacement/truncation/deletion of the directory entry does not invalidate a private mapping because the retained file-data generation remains alive until the mapping is destroyed. MUDOS_FILE_MAP_SHARED creates a live shared mapping of the current file object. Read-only shared mappings fault data lazily and observe writeback-coherent file-page state. A writable shared mapping is accepted only when the caller has ordinary VFS write permission for the complete file and the filesystem supports coherent mapped writeback. Dirty shared pages are written back through the normal VFS/filesystem path and therefore obey FACIOS transaction, batching, allocation, journaling and durability rules rather than bypassing them. Shared mappings participate in one coherent per-file page-cache/writeback view: normal mudos_file_write() operations and writable shared-mapping dirties serialize their overlapping page/range updates under the file mapping/VFS ownership rules, non-overlapping changes are merged into the latest visible file-data generation, and overlapping bytes follow the last serialized writer rather than replacing an unrelated older whole-file snapshot. mudos_memory_sync() writes dirty shared mapped ranges back; MUDOS_MEMORY_SYNC_DURABLE additionally waits until the affected FACIOS state is durably committed/storage-flushed. Normal unmap may schedule ordinary writeback but does not imply durable storage unless durable sync was requested first.


To keep truncation semantics deterministic and simple, a file may not be truncated below the highest byte covered by any live writable shared mapping; such a truncate returns MUDOS_ERROR_BUSY. Read-only shared mappings and private snapshot mappings do not block truncation. Deleting or renaming an entry does not invalidate an already retained mapping object. External NTFS/FAT32/exFAT mappings use the same VFS permission rules but MUDOS_FILE_MAP_SHARED|WRITE is reported unsupported when the mounted filesystem driver cannot provide coherent page-cache/writeback semantics; private mappings remain available. File-backed executable mappings must be private, never writable, and are validated as Ring-3 executable ranges. A clean file-backed page is reconstructible and may be reclaimed without allocating FACIOS paging space. Private COW pages which have diverged from the file become ordinary anonymous-derived pages and may use the existing disk-paging path. File-backed pages, shared mappings and module text pages remain ineligible as new memory-deduplication source pages because the memory deduplicator remains restricted to anonymous private Ring-3 pages.


Every mapping has a non-zero internal mapping generation and is owned by exactly one process. Page faults retain the mapping object before starting storage I/O. Concurrent unmap, process termination and page fault synchronize through the process page_table_lock plus mapping reference/state lock so the mapping cannot disappear while an I/O completion still refers to it. A file page is installed only after the read completed successfully and the mapping generation/file-data identity is revalidated. Failed file-backed page-in becomes a mapped-I/O access failure for the affected process rather than exposing partial data. Shared dirty writeback pins the page until the corresponding filesystem operation has accepted the data; a failed writeback keeps the dirty page authoritative and propagates the I/O/storage error. TLB generation/shootdown follows the existing MUDOS_64 page-table protocol for every map, protection, COW and unmap transition.


Memory Deduplicator: MUDOS_64 uses exactly one incremental memory-deduplication scanner. Because the kernel is tickless, the scanner computes its next deadline as "now + 16ms" after each scan and registers it with the scanner-owning CPU's one-shot LAPIC deadline system described above; the LAPIC remains armed for whichever registered deadline, including the running thread's non-deferrable EEVDF request deadline when applicable, is nearest. Each completed scan examines exactly the next 512 physical 4 KiB page slots through a persistent round-robin cursor; unavailable and ineligible slots still count, the cursor wraps after the final slot, scans never overlap because the next deadline is scheduled only after the previous scan completes. Each accepted scan starts with 0 attempted merges and may start at most 128. An attempt begins when a same-hash candidate exists and candidate validation starts; successful, failed, stale, canceled, allocation-ID-mismatching, eligibility-mismatching, final-hash-mismatching and "memcmp"-mismatching attempts all consume the limit. After attempt 128 the scanner still advances through the remaining slots to complete the fixed 512-slot scan but starts no more merges. Only present, writable, non-executable, normally cached, anonymous private Ring 3 pages with exactly one active PTE mapping are eligible as newly scanned deduplication source pages. Deduplication is restricted to one kernel-controlled application family: a source page may be compared or merged only with a candidate whose owning process has the exact same complete "application_id". Separate process instances with the same "application_id" may therefore deduplicate with each other, while processes with different "application_id" values are never compared or shared even when their contents are identical. Kernel/system-reserved pages, page tables, DMA, MMIO, framebuffer/device mappings, shared memory, executable pages, loader-transition pages, pages involved in allocation/freeing or I/O, pages with unsupported cache/sharing semantics, pages with more than one mapping and pages pinned by another operation are ignored as scan sources. An already deduplication-shared page is never selected as a newly scanned source page, but a physical page which is already the read-only PTE_SOFTWARE_COW canonical page of an earlier successful deduplication merge may remain in the deduplication hash table as a canonical merge target while its mapping count is below 32. Such a canonical target does not require a single-owner record because its deduplicated mappings may belong to multiple process instances of the same application family, while its deduplication hash entry retains that exact complete "application_id"; it is valid only while its allocation ID, canonical runtime flag, read-only/COW state, mapping count, pin state and retained hash-entry application identity remain valid. Every process mapping newly merged into that canonical must have an "application_id" exactly equal to the canonical hash entry its "application_id". Deduplication may never increase one canonical physical page above 32 active mappings; a candidate merge which would increase its mapping count above 32 is rejected without changing mappings or counts, and a canonical hash-table reference is invalidated when that canonical reaches 32 mappings. An entry referring to the exact same physical page and allocation ID is ignored without consuming a merge attempt. A potentially eligible source page is pinned, its metadata and owning process are retained and a preliminary content hash is calculated while normal writes may still race. With no same-hash same-application candidate, the table entry is inserted/replaced together with the source process its complete "application_id" and all temporary ownership is released. With a candidate and remaining attempt budget, the attempt counter is incremented before candidate pinning/validation. The candidate is allocation-ID-pinned and then classified during validation as either another singly mapped private source-style candidate whose retained owning process has an "application_id" exactly equal to the source process its "application_id" or an existing deduplication canonical target whose hash-entry "application_id" exactly equals the source process its "application_id". Actual comparison and merging use the ordered process page-table locks and physical-page striped locks described below; because there is exactly one scanner, no global memory-deduplication lock is used. The global order is "lower process page_table_lock > higher process page_table_lock > lower physical-page striped-lock index > higher physical-page striped-lock index"; processes are ordered by PID then process instance ID, mappings within one process by virtual address and physical pages by page number. The same process lock is acquired once. When both pages are singly mapped private pages, both applicable process page-table locks are acquired in that order when they belong to different process instances, while one page-table lock is acquired once when both pages belong to the same process. When the candidate is an already-established canonical target, only the newly scanned source page its process page_table_lock is required because the canonical contents are already globally read-only through PTE_SOFTWARE_COW and may only change by a writer receiving a separate replacement page. No deduplication or copy-on-write path acquires a page-table lock while holding a physical-page lock. Retained process references plus page-table locks keep applicable process objects and page-table hierarchies alive during the operation. After acquiring the ordered locks, the scanner fully revalidates the applicable process identities/states, application IDs, allocation IDs, metadata, pins and PTEs. The newly scanned source process must remain PROCESS_ALIVE, must still have the exact "application_id" captured for the attempt and its PTE must still map the expected singly mapped eligible private page. A private candidate process must satisfy the same rules, its "application_id" must exactly equal the source process its "application_id" and its PTE must still map the expected singly mapped eligible private page. An existing canonical candidate instead must still have the expected allocation ID, canonical runtime flag, valid mapping count below 32, read-only PTE_SOFTWARE_COW canonical state and a hash-entry "application_id" exactly equal to the source process its "application_id". For a private/private comparison, both PTEs are changed to read-only while preserving all other permission/cache bits. For a source/canonical comparison, only the writable source PTE is changed to read-only because the canonical mappings are already read-only. After those page-table permission changes have been published, the applicable process its "tlb_generation" is incremented with release ordering, followed by local invalidation and an acknowledged TLB shootdown for every changed process/address pair to only the CPUs which may still be actively executing the affected address space. The process active-CPU bitmap is maintained atomically by context switching: a CPU publishes its active bit before it may execute Ring 3 in that process, validates its CPU-local PCID binding and the process tlb_generation after publishing that bit and rechecks the generation before IRETQ; a CPU clears the bit only after it can no longer execute or access the old Ring 3 address space as its current process. A shootdown takes the active-CPU snapshot only after the page-table change has been published and tlb_generation has been incremented, so a CPU racing into the process is either included in the shootdown or observes the newer generation and invalidates its CPU-local PCID binding for that process before Ring 3 execution. CPUs which are not currently executing the affected process do not need an immediate IPI; any CPU-local PCID binding cached for that process retains the older observed tlb_generation and is invalidated lazily with INVPCID before that address space may run there again. On CPUs without PCID/INVPCID support, the same active-CPU generation protocol is used with ordinary CR3/INVLPG invalidation semantics. After write protection is globally visible to every CPU which can currently execute the changed mappings, both hashes are recalculated and a byte-for-byte "memcmp" is performed. If contents differ, every source/private-candidate PTE made read-only by this attempt is restored to its original writable state, the applicable tlb_generation is incremented and another acknowledged active-CPU shootdown completes before cancellation. If two private pages match, the lower-numbered physical page becomes canonical, its "mapping_count" is increased before redirecting the duplicate PTE, its runtime metadata is marked as a deduplication canonical, both mappings remain present/read-only and receive the software-defined "PTE_SOFTWARE_COW" bit, the applicable tlb_generation is incremented, the acknowledged active-CPU shootdown completes and only then is the duplicate page its mapping count decreased. The hash entry is updated to the canonical page/allocation ID while retaining the same complete "application_id" and remains usable only for later identical source pages belonging to processes with that same "application_id" while its canonical mapping count remains below 32. If a source page matches an already-established canonical target belonging to that same application identity, the canonical page remains canonical regardless of physical-page number, its mapping_count is increased before redirecting the source PTE to it, the redirected mapping is published read-only with PTE_SOFTWARE_COW, the source process its tlb_generation is incremented, the acknowledged active-CPU shootdown completes and only then is the former source page its mapping count decreased. When either successful path makes the canonical mapping_count exactly 32, the hash entry referring to that canonical is invalidated so no additional merge can increase it further. A duplicate/source physical page is freed only after both mapping and pin counts reach 0. A write fault is deduplication copy-on-write only when the fault was a write and the PTE is present, read-only and marked "PTE_SOFTWARE_COW"; every other fault retains normal protection-fault behaviour. The handler pins the canonical page and allocates a replacement page before locking, then acquires the faulting process its "page_table_lock" and the required distinct physical-page striped locks in lock-index order, revalidates the mapping/allocation-ID/COW state, copies the contents, initializes the replacement metadata and sets its "mapping_count" to 1 before publishing the new PTE. The faulting PTE is redirected to the replacement, "PTE_SOFTWARE_COW" is cleared, writable permission is restored, the process its tlb_generation is incremented, the required acknowledged active-CPU shootdown completes and only then is the canonical mapping count decreased. If revalidation fails because another thread already resolved the fault, the unused replacement is released and the current PTE state is retried or accepted. If COW replacement-page allocation initially fails, normal memory-pressure recovery is performed and allocation is retried. Recovery first rejects optional work, reclaims eligible clean caches and cancels unaccepted temporary work. If a replacement page still cannot be obtained, the faulting process is terminated while the canonical page and all unaffected mappings remain valid. Every Ring 0 path writing to Ring 3 memory uses the target process its "page_table_lock" and validates the current PTE. A normal private mapping may be written while that lock remains held. A COW mapping requires releasing the lock, calling "cow_resolve_page(process, virtual_address)" and restarting validation; Ring 0 may never bypass COW through a direct physical mapping. The synchronized page-table locks therefore prevent Ring 0 and Ring 3 writers from modifying pages during final comparison/merge. TLB shootdowns use one preallocated outbound request owned by each logical CPU instead of one globally serialized request. Every source CPU its request contains a non-zero monotonically increasing generation, "address_count" of exactly 1 or 2, up to two process identities/TLB generations/virtual addresses and one acknowledgement-generation slot per logical CPU; when both addresses belong to one deduplication operation, the two entries may carry the same process identity or two different process identities whose "application_id" values are exactly equal. Each target CPU owns an atomic pending-source bitmap. The initiating CPU fills and publishes only its own request with release ordering, sets its source bit in each required target CPU its pending-source bitmap, sends the required IPIs and waits with acquire loads until every selected target acknowledges that exact request generation. Different source CPUs may therefore have independent TLB shootdowns in flight concurrently and no global TLB-shootdown lock exists; one source CPU does not reuse its own outbound request until its previous generation is fully acknowledged. Generation wrap at UINT64_MAX causes "RING 0 EXECUTION ERROR". The IPI handler repeatedly atomically obtains and clears the pending source bits, loads each corresponding source request with acquire ordering, processes exactly "address_count", validates whether each requested process identity is currently active on that CPU, resolves the exact CPU-local PCID binding for that process when one is active, invalidates applicable local translations using INVPCID individual-address or single-context invalidation as required (or the non-PCID fallback), and only after an invalidation sufficient for that requested process identity updates that local PCID slot its observed TLB generation. If a requested address space is no longer active on that CPU and therefore requires no immediate invalidation, the CPU acknowledges the request without advancing the observed TLB generation in any CPU-local PCID slot cached for that process, so a later switch into that address space still detects the older observed generation and invalidates before Ring 3 execution; if that cached slot is evicted first, rebinding already performs the required single-context invalidation. The handler executes the ordering barrier and acknowledges that source request generation with release ordering, then checks the pending-source bitmap again and continues until it is empty. Shootdown requests published before the handler its final empty pending-source observation are drained before that handler invocation returns; a request published after that final empty observation remains pending and its IPI causes another handler invocation. It never acquires page-table locks, physical-page locks, allocator locks, runqueue locks, mutex locks or filesystem locks. Every scan, merge and copy-on-write success, failure or cancellation path releases every pin, process reference, lock and unused replacement page it owns. Local interrupt disabling alone is never sufficient synchronization; retained references, ordered locks, allocation-ID-aware pinning, mapping metadata, "PTE_SOFTWARE_COW", CPU-local PCID binding/pcid_generation tracking, process TLB generations, active-CPU tracking and generation-tagged acknowledged per-CPU TLB shootdowns provide SMP safety. Native built-in Unicode font engine which uses Liberation Sans Regular as the primary font style for all normal system and .MEXE/.ROOT program text together with a fixed built-in fallback font set for characters not present in Liberation Sans. The Liberation Sans and fallback font data, glyph measurements, kerning information, shaping tables and Unicode lookup data are converted into compact read-only vector outline data during compilation and stored directly inside the MUDOS_64 system image, so no external font files, runtime font parsing, font loading or user-selectable font switching are used. Input and application-visible text uses UTF-8. The text engine strictly decodes UTF-8 into Unicode scalar values from U+0000 through U+10FFFF excluding surrogate code points; malformed UTF-8 presented for rendering is replaced with U+FFFD without reading beyond the validated input range. The built-in font set provides wide Unicode coverage including ASCII, Latin and Latin Extended, Greek, Cyrillic, Armenian, Georgian, Hebrew, Arabic, common Indic scripts including Devanagari and Bengali, Thai, Hiragana, Katakana, Hangul, commonly used CJK Unified Ideographs, general punctuation, currency symbols, mathematical symbols, arrows, box-drawing characters, technical symbols, dingbats and a broad monochrome emoji/symbol subset. Characters which are valid Unicode but have no glyph in any built-in font use a visible replacement/missing-glyph symbol while the original UTF-8 data remains unchanged. Newline, carriage return and tab are supported as text-layout controls. Text segmentation is Unicode-aware: combining marks remain attached to their base character, editing/cursor movement, deletion, selection, clipping and ellipsis operations do not intentionally split a valid UTF-8 sequence or grapheme cluster, and text measurement operates on the shaped glyph sequence rather than assuming one byte or one code point equals one displayed character. The layout engine supports left-to-right and right-to-left text with bidirectional run ordering, combining-mark positioning, contextual Arabic joining and presentation, common ligatures, and the contextual glyph substitution/reordering needed by the supported Indic scripts. Font fallback is resolved deterministically per shaped text run so the same valid input produces the same glyph sequence on every MUDOS_64 installation. Each visible glyph is stored as a scalable vector outline made from straight lines and curved sections. The engine scales these outlines to any supported integer pixel height from 8 to 256 pixels using deterministic fixed-point calculations. Curved sections are repeatedly subdivided until their maximum deviation from the resulting straight line is no more than 0.25 output pixels, with a fixed maximum subdivision depth of 8 to keep rasterization work bounded. The resulting outline is rasterized using 4x4 supersampling, giving every output pixel an 8-bit coverage value from fully transparent to fully visible and creating smooth grayscale anti-aliased letter edges at both small and large sizes. The resulting glyph pixels are alpha-blended into the existing RGBA window and compositor surfaces. Rasterized glyphs are cached using their built-in font-face ID, glyph ID and requested pixel height so commonly used glyphs do not need to be rasterized repeatedly. The font cache uses a fixed maximum of 512 entries and a fixed 4 MiB bitmap memory area. When the bitmap area becomes full, the complete cache is cleared between complete text-rendering operations and reused, keeping memory usage and replacement behaviour simple and strictly bounded. System and .MEXE/.ROOT text-drawing requests are submitted to the Font Engine thread and processed through the normal UI event and invalidation path. Font rasterization, cache access and text rendering are executed exclusively by the Font Engine thread, making the cache single-owner and preventing concurrent cache modification without requiring another lock. Text measurement only reads the immutable built-in Unicode lookup, character measurement, kerning and shaping information and may be executed synchronously by the calling system or program thread without accessing the glyph cache. The font engine includes the normal Liberation Sans character widths, spacing, baseline measurements and kerning information so character pairs such as AV, To and Yo are positioned correctly while the fallback fonts provide their corresponding script-specific metrics and shaping data. It supports text measurement, left-positioned text, centered text, clipped text, multiple lines, tabs, bidirectional text and shortening text with three dots when it does not fit inside the available area. A separate minimal built-in bitmap character renderer remains available only for early startup, kernel panic output and severe system failure situations where the normal UI Unicode font engine cannot safely operate. FACIOS stands for "Fully Atomic Compressed I/O System". For the transparent on-the-fly compression FACIOS uses the custom algorithm: "XCDA-256” (stands for "Extreme Compressor/Decompressor Algorithm with 256 KiB") is a lossless compression algorithm using LZ77, Huffman coding, and Finite State Entropy (FSE). The compressor uses a 256 KiB sliding window to store previously processed data and search for repeated byte sequences. The LZ77 stage uses a hash chain match finder to locate previous occurrences of data inside the sliding window. The compressor searches the hash chains for possible matches and selects matches based on length and distance. Lazy matching is used by checking whether delaying the current match allows a longer or more efficient match to be encoded. The LZ77 encoder converts input data into sequences containing literal data, literal lengths, match lengths, and offsets. Literal bytes are compressed using Huffman coding, while literal lengths, match lengths, and offset symbols are compressed using FSE. The compressor maintains a cache of eight recent offsets. When a match uses an offset that exists in the cache, it is encoded as a reference to that offset instead of storing the full value. New offsets are inserted as the newest entry while older offsets are shifted down. The eight recent offset references are encoded as REP0, REP1, REP2, REP3, REP4, REP5, REP6 and REP7. Data is processed in independent 256 KiB frames divided into 8 32 KiB blocks. Each 32 KiB block is encoded separately, then compared against its original size. If the compressed block does not reduce the total size (including metadata) by at least 5%, the compressed result is discarded and the original block is stored instead. Compressed blocks contain new Huffman/FSE tables or explicit frame-local table-reuse markers together with the encoded LZ77 sequence data required for decompression. Raw blocks contain the original uncompressed data. The decompressor reads each block and determines whether it contains compressed or raw data. For compressed blocks, it reconstructs the Huffman and FSE decoding states, decodes literals and LZ77 sequences, resolves recent offset references, and copies matched sequences from the 256 KiB sliding window. The decompressor continuously updates the frame-local sliding window with reconstructed data, allowing later blocks in the same frame to reference previously decoded content; decoding a new frame requires no earlier frame. XCDA-256 uses a 256 KiB LZ77 window, hash chain matching, lazy matching, eight-entry recent offset reuse, Huffman literal encoding, FSE sequence encoding, and requires at least a 5% reduction (including metadata) before storing compressed data. Uses a search depth of 16 candidates. Uses a block size of 32 KiB. Minimum match is 3 bytes. Maximum match is 8192 bytes. Hash table has 65536 entries, the hash has 3-byte rolling hash and the chain is 32-bit offsets. Evaluates maximally 8 future matches. Match length FSE table log: 8. Offset FSE table log: 8. Uses bounded optimal parsing over maximally 8 future matches. Utilizes table reuse.". Each XCDA-256 logical 32 KiB block is represented by one "struct facios_block_reference" stored in the file-data version its fixed-fanout radix block map. FACIOS block indexes are resolved through at most FACIOS_BLOCK_MAP_LEVELS = 9 levels with 6 index bits per level and FACIOS_BLOCK_MAP_FANOUT = 64, so a logical block lookup performs at most 9 fixed pointer/index steps and remains bounded O(1) for the complete uint64_t file-size domain. Level 0 is a leaf containing up to 64 "struct facios_block_reference" values and higher levels contain up to 64 child-node pointers. Block-map nodes are allocated only for paths which exist and every node is immutable after it has been published into a file-data version. Each block-map node has its own reference count; unchanged nodes may be shared by multiple immutable file-data generations, while a modified logical block copies only its affected leaf and the at most 8 ancestor nodes required to construct the new root. Modifying multiple blocks in the same replacement reuses each newly copied common ancestor within that replacement instead of copying the same path repeatedly. Therefore constructing a replacement file-data version does not copy metadata proportional to the complete file size. Its raw or compressed payload is stored in one contiguous extent of 16 KiB FACIOS physical blocks beginning at "physical_start_block", with "physical_block_count = ceil(stored_size/16384)". "stored_size" is the exact encoded byte count, "logical_size" is the exact uncompressed byte count, "stored_checksum" is the CRC64-ECMA checksum of the exact stored payload, "logical_checksum" is the CRC64-ECMA checksum of the exact uncompressed contents, "compression_version" is 0 for raw blocks and 1 for the current XCDA-256 format, "frame_block_index" identifies block 0 through 7 inside its 256 KiB frame and "flags" identifies raw, compressed and frame-local entropy-table reuse state. Raw blocks use "stored_size = logical_size". Every read validates "stored_checksum" before decompression and validates "logical_checksum" after decompression; a checksum mismatch rejects the block as an I/O error and causes the affected FACIOS volume to mount or remain read-only instead of returning unverified data. Unused bytes in the final physical 16 KiB block are zeroed and are not part of the encoded payload. Separate block payloads never share a physical 16 KiB allocation range. Compression therefore saves storage in 16 KiB increments without requiring variable payloads to be packed together inside one physical allocation block. "block_generation" is non-zero and changes whenever that stored extent is replaced. FACIOS keeps every stored extent immutable and maintains reference accounting for each extent independently from "mudos_file_data.references" and the block-map node references. Every file-data version, pending transaction, journal-recovery record and active reader retains the block-map root and therefore every block-map node and stored extent it references, and a block-map node or stored extent is reclaimed only when no such reference remains. Unchanged block-map subtrees and unchanged stored extents may therefore be reused by multiple complete replacement file-data versions without being copied or reclaimed while still referenced. For every file write, FACIOS constructs a complete replacement file-data object privately, constructs only the changed immutable block-map leaves/ancestor paths while retaining unchanged subtrees from the immediately preceding version, and publishes it as the latest volatile-visible file-data version through one generation-validated pointer swap under the applicable VFS entry stripe lock after the complete replacement has been accepted into the bounded in-memory write batch, so readers observe either the complete old version or the complete replacement and reads see the accepted replacement immediately. FACIOS separately tracks the latest durable file-data generation. Failed preparation leaves the old version unchanged, and replaced data remains allocated until its reader reference count, every block-map node reference count and every stored-extent reference count reach 0. Multiple pending writes to the same file form one ordered generation chain. Each transaction its previous state is the immediately preceding visible version, every pending version retains its own transaction ID and independently recoverable journal records, and the transactions are committed in that order without coalescing. An immediate durable commit request for a later pending version also commits every required predecessor, and no pending version, block-map node or stored extent is reclaimed while an active reader, later transaction or journal-recovery record still references it. FACIOS volumes use one fixed-size circular journal with non-zero monotonically increasing transaction IDs; every journal record is length-delimited and checksummed. Before changing durable published metadata, every transaction contributes a record containing its previous state, replacement state and affected allocations to its group, all group journal-intent records are written and share one flush, all replacement data is then written and shares one flush and all commit records are finally written and share one flush, with each transaction its commit record remaining its persistent atomicity point. FACIOS then durably publishes all replacement metadata in the group and shares one flush, advances the latest durable file-data generation, records completion and only afterward reclaims old blocks, unreferenced block-map nodes and journal space. During mount, uncommitted transactions are rolled back while committed but incomplete transactions are completed; after an unclean shutdown recovery may therefore restore an older durable generation even when running processes had previously observed a newer volatile-visible generation. Corrupt or ambiguous journal data causes the persistent volume to mount read-only or fail instead of guessing. These guarantees apply only to FACIOS volumes, not NTFS, FAT32 or exFAT. IPC implementation: Type: asynchronous fixed-size message queues + shared memory. Each PID has its own 512-message ring queue using O(1) head/tail operations, with each message containing sender PID, sender instance ID, destination PID, destination instance ID, 32-bit message type, 32-bit payload size and up to 96 bytes of copied data. Sending and receiving temporarily disables interrupts and uses a per-queue spinlock. Full queues reject new messages. Process instance IDs prevent old messages from being delivered after PID reuse. Receiving is non-blocking. "mudos_ipc_wait()" is the minimal blocking wait operation: it acquires the calling process its IPC queue lock, returns immediately when the queue is not empty and otherwise appends the current thread to that queue its strict FIFO IPC waiter list through "ipc_wait_next", gives the queue its required thread reference and atomically changes the caller from THREAD_RUNNING to THREAD_BLOCKED with THREAD_BLOCK_IPC through the scheduler while preventing a sender from publishing a message between the empty check and waiter publication. A successful sender publishes the complete message before detaching and waking the oldest valid IPC waiter, and runqueue ownership is established before the queue-owned waiter reference is released. Therefore there is no lost-wakeup window. "mudos_ipc_wait()" returns only after a message has been published or the process is terminating; the caller then uses the existing non-blocking "mudos_ipc_receive()" to consume it. External .MEXE and .ROOT programs expose mudos_ipc_send(), mudos_ipc_receive(), mudos_ipc_wait(), mudos_shared_page_map(), mudos_shared_page_retain() and mudos_shared_page_release(); fixed validation and per-process limits apply to every operation. Larger data uses up to 64 reference-counted 4 KiB shared pages which can be retained, released and mapped into process address spaces. Process exit detaches every IPC waiter under the queue lock, marks it for termination under the locks owning its thread state, releases every queue-owned waiter reference, releases every shared-page reference owned by that process, and a shared page is freed only when its total reference count reaches zero; reference-count overflow or underflow causes "RING 0 EXECUTION ERROR".


Byte-stream/pipe objects: MUDOS_64 provides a native unidirectional kernel byte stream exposed as a read endpoint and a write endpoint. mudos_pipe_create() creates one stream and returns one opaque generation-safe read-end handle plus one opaque generation-safe write-end handle. The stream has no message boundaries and preserves byte order exactly. Its capacity is fixed at MUDOS_PIPE_CAPACITY_BYTES=65536 bytes, implemented as at most sixteen 4 KiB buffer pages allocated lazily as data enters the pipe rather than reserving 64 KiB for every empty pipe. Each stream owns one spinlock, byte head/tail/count state, read-end and write-end reference counts and strict FIFO reader/writer wait queues. A non-blocking read returns immediately with available bytes, MUDOS_ERROR_WOULD_BLOCK when empty while at least one writer still exists, and MUDOS_ERROR_END when the stream is empty and the last write endpoint has been released. A non-blocking write writes as many bytes as fit and returns MUDOS_ERROR_WOULD_BLOCK only when no byte can be accepted; if no read endpoint remains it returns MUDOS_ERROR_BROKEN_PIPE. Blocking read/write operations sleep with THREAD_BLOCK_PIPE and wake only after the state that can make forward progress has been published. One read or write call may complete partially; callers requiring an exact byte count loop until complete. Pipe writes are never treated as atomic messages. Releasing the final writer publishes end-of-stream and wakes readers, while releasing the final reader publishes closed-reader state and wakes writers. A stream is destroyed only when all endpoint references, in-flight operations and wait registrations are gone.


Pipe handles identify a global generation-safe endpoint object, while each process separately owns authorization/reference state for that endpoint. mudos_pipe_retain() may grant the same endpoint handle to a destination process the caller is allowed to communicate with; after the grant succeeds the numeric handle can be carried in the existing copied IPC payload and resolves in the destination only because the kernel has already installed the destination reference. A process may never manufacture pipe rights by guessing a handle. Process termination releases every pipe endpoint reference owned by that process and detaches its direct pipe waiters.


Wait-many/completion mechanism: MUDOS_64 provides one generic wait-any primitive, mudos_wait_many(), for up to MUDOS_MAX_WAIT_MANY_ITEMS=64 objects in one call. The initial waitable object types are manual-reset events, threads, processes, the calling process its IPC queue, pipe endpoints and completion queues. Every wait item contains a fixed object type, requested event mask, two 64-bit object-identity words and one caller-chosen 64-bit user tag. Thread/process items place TID/PID in object0 and the corresponding instance ID in object1; 64-bit opaque handles use object0 and zero object1; the current IPC queue uses both object words as zero. The call first validates and retains every referenced object. Readiness is then checked under the applicable object locks in a deterministic kernel object-ID order. If one or more items are already ready, the lowest input index is returned deterministically without blocking. In mudos_wait_result, status is MUDOS_OK for ordinary readiness or the applicable object-level error state, information is zero for events/threads/processes and may report currently available bytes for pipes or queued-record/message count for completion/IPC objects, and user_tag is copied from the selected input item.


When no item is ready, mudos_wait_many() creates one kernel wait_context and one lightweight registration per item, publishes every registration before the thread becomes unschedulable and then atomically blocks the caller with THREAD_BLOCK_WAIT_MANY. Each waitable object increments a non-zero 64-bit wait_sequence whenever a change can satisfy a waiter. Registration records retain the sampled sequence, object reference, requested events, input index and wait_context reference. A producer publishes the new object state first and then, while holding that object its wait lock, tries one atomic pending->completed transition on each applicable wait_context. Exactly one trigger, timeout or termination path can win a wait_context. The winning path stores the ready index/events/status/information before scheduler_wake_thread(); losing triggers do not wake the same thread again. Cleanup removes every remaining registration under the same deterministic object-lock ordering and releases all references before the wait_context is reclaimed. An object-state change between the initial readiness check and registration cannot be lost because sequence/state is revalidated after registration and before blocking. Timeouts use the normal absolute tickless scheduler deadline system. Wait-many does not consume an event, process completion, IPC message or pipe byte by itself; it reports readiness and the caller then performs the corresponding operation. A process/thread termination item is level-ready once that target completion has been published. This design avoids polling and does not require one permanent waiter thread per object.


A native completion queue is a process-local generation-safe object with a fixed 256-record FIFO. Each record contains a caller/kernel supplied 64-bit user_tag, one int64_t result and one uint64_t information value. mudos_completion_post() publishes one complete record or returns MUDOS_ERROR_QUEUE_FULL without overwriting an older record; mudos_completion_receive() removes the oldest record non-blockingly; and mudos_completion_wait() blocks with THREAD_BLOCK_COMPLETION until at least one record exists, timeout occurs or the process terminates. A completion queue is also waitable through mudos_wait_many(). Kernel subsystems may retain an internal completion reference for future asynchronous ABI operations; any operation which promises an eventual kernel completion must reserve the required queue capacity/reference at submission time so a full completion queue can never cause a completed kernel operation to disappear. Destroying a completion queue is rejected while an in-flight kernel operation still owns a completion reference, and normal process termination cancels/detaches those operations before the object is released.

The scheduler uses a Red-black tree keyed on "virtual_deadline" with PID then TID as tiebreakers, with "struct runqueue    
{    
    spinlock_t lock;    
    struct rb_node *root;    
    struct rb_node *eligibility_root;    
    uint64_t total_runnable_weight;    
    uint64_t virtual_time;    
    uint32_t runnable_count;    
};" implementation; each THREAD_READY tree entry stores "subtree_min_vruntime" so the earliest eligible virtual deadline can be selected by skipping subtrees whose minimum task_virtual_runtime is greater than virtual_time, making selection, insertion and removal O(log(runnable_count)). Every currently ineligible THREAD_READY thread is also indexed in "eligibility_root" through its separate "eligibility_node", keyed on task_virtual_runtime with PID then TID as tiebreakers, so the lowest future task_virtual_runtime and therefore the next eligibility crossing can be found in O(log(runnable_count)) without scanning the deadline tree. When virtual_time reaches that value the applicable now-eligible threads are removed only from the auxiliary eligibility tree and remain in the deadline tree for normal earliest-eligible-virtual-deadline selection. runnable_count and total_runnable_weight include the current THREAD_RUNNING thread plus all THREAD_READY threads assigned to that CPU while the RUNNING thread itself is not simultaneously stored as a READY tree node. System extension programs use .ROOT, which is a separate runtime program format and is not built into the MUDOS_64 system image, and carry "trust_level" PROCESS_TRUST_ROOT, .ROOT has broad low-level system access and should thus be handled very carefully, third-party .ROOT programs are not recommended unless it's a trusted source because of that. The ".ROOT" format uses the magic: ROOT_v1.3 (the loader also accepts legacy ROOT_v1.2 as a zero-static-TLS image), architecture: x86_64, Endianness: Little Endian, executable type: Ring 3 User Program, initialized data size: bytes, BSS size: bytes, code size: bytes, entry offset: 64-bit offset from randomized image load base, initial stack size: 4 KiB (dynamically grows on page faults with lazy allocate), max_stack_size: 512 MiB, heap size: starts at 0 and grows on demand, TLS template offset: 64-bit file offset, TLS initialized size: 64-bit bytes, TLS total size: 64-bit bytes, TLS alignment: validated power-of-two, optional dynamic-module export table: case-sensitive named Ring-3 symbols, only timestamp and file size flags used. Per the permission rule above, .ROOT programs can read/create/write/rename/move/delete files, kill or launch programs and call fixed validated privileged syscalls for file management, process control and power control; they never directly access kernel memory or hardware. The ".MEXE" format uses the magic: MEXE_v1.9 (the loader also accepts legacy MEXE_v1.8 as a zero-static-TLS image), architecture: x86_64, Endianness: Little Endian, executable type: Ring 3 User Program, initialized data size: bytes, BSS size: bytes, code size: bytes, entry offset: 64-bit offset from randomized image load base, initial stack size: 4 KiB (dynamically grows on page faults with lazy allocate), max_stack_size: 512 MiB, heap size: starts at 0 and grows on demand, TLS template offset: 64-bit file offset, TLS initialized size: 64-bit bytes, TLS total size: 64-bit bytes, TLS alignment: validated power-of-two, optional dynamic-module export table: case-sensitive named Ring-3 symbols, only timestamp and file size flags used, carries "trust_level" PROCESS_TRUST_MEXE, receives a kernel-computed SHA-256 "executable_hash" and a kernel-controlled stable "application_id", and per the permission rule above can read/create/write/delete/rename/move only entries owned by the same application family, while MUDOS_VFS_PERMISSION_GLOBAL entries can be read/written/deleted/renamed/moved by it without permission restriction, subject to normal filesystem state, synchronization, capacity and I/O errors. Dynamically loadable Ring-3 libraries/modules use the ".MLIB" format with magic MLIB_v1.0, architecture x86_64, little endian and position-independent Ring-3 code only. An .MLIB is never launched as a process by double-click or mudos_open_entry(); it is mapped only into an already existing .MEXE or .ROOT process through the module ABI. The format contains validated loadable segment descriptors, a case-sensitive UTF-8 module name, export table, import table, relocation table, optional initializer/finalizer entry offsets and optional TLS template offset/initialized-size/total-size/alignment. The initial relocation set is intentionally limited to the x86-64 relocations required for position-independent C modules: base-relative relocation, 64-bit absolute data relocation, GLOB_DAT, JUMP_SLOT and the MUDOS dynamic-TLS module/offset relocations. Text relocations are forbidden. Relocation targets must lie in writable non-executable relocation/GOT/data pages while binding occurs; pages declared read-only-after-relocation are sealed read-only before the module becomes visible to Ring 3. No relocation may create a writable+executable page.


mudos_module_load() takes a complete mudos_entry_handle selected by the caller, validates the complete .MLIB before publication, computes the module's SHA-256 hash for identity/debugging, chooses a randomized non-overlapping load base, creates private file-backed mappings for immutable code/read-only data and private COW/zero-backed mappings for writable data/BSS, registers the optional dynamic TLS template and eagerly resolves imports. The kernel never searches hardcoded filesystem paths for libraries. Dependencies are loaded explicitly by the Ring-3 program/runtime first; an MLIB import may optionally name the provider module and otherwise resolves against the main executable exports followed by already loaded modules in deterministic load order. Missing or ambiguous required imports reject the load without publishing a partially usable module. Circular dependency groups requiring unresolved forward imports are intentionally unsupported in MLIB_v1.0; a Ring-3 library manager must order modules so each load can be completely resolved. Initializer/finalizer functions are not invoked in Ring 0. After successful load, mudos_module_get_info() exposes validated Ring-3 initializer/finalizer addresses and the Ring-3 runtime calls them in process context.


Every module handle is process-local, opaque, non-zero and generation-safe. Module export lookup returns either a code/data address or a TLS offset/type; TLS symbols are resolved to the calling thread through mudos_module_tls_address(). Module mappings inherit the host process address space and therefore cannot elevate privilege: code loaded into a .MEXE executes with exactly that .MEXE process's permissions, while code loaded into a .ROOT executes with that ROOT process's broader authority. Because loading untrusted code into a ROOT would inherit ROOT privilege, a ROOT process may load an .MLIB only when the module file has MUDOS_VFS_PERMISSION_ROOT and creator_trust_level PROCESS_TRUST_ROOT, or when the kernel-owned direct-user-action trust path has explicitly established equivalent ROOT trust. A ROOT may not dynamically load GLOBAL or MEXE-tier module code. A .MEXE may load a GLOBAL .MLIB or a MUDOS_VFS_PERMISSION_MEXE .MLIB whose creator_application_id exactly equals the host process application_id; it may not load another application family its private module. The normal executable/module header, range, W^X and file permission checks are repeated at load time.


Module unload first marks the handle unloading so no new symbol/TLS resolutions can begin, rejects unload while another loaded module retains it as a resolved dependency, and rejects unload while any process thread currently has RIP inside one of the module's executable ranges. The Ring-3 runtime is responsible for stopping its own calls, running the module finalizer and ensuring it has not retained stale function/data pointers before requesting unload. The kernel cannot prove that arbitrary user memory contains no stale pointer. After those conditions are met, the module TLS generation is invalidated, per-thread dynamic TLS storage for that module is released, executable/data mappings are unmapped with normal TLB synchronization, dependency references are dropped and the module slot generation increments. A stale module handle or later use of an unmapped stale function pointer cannot resolve to a newer module and results in the normal invalid-handle or Ring-3 memory-fault behavior. Read-only MLIB file-backed pages may be physically shared through the normal file page cache between processes loading the exact same immutable file-data generation while each process retains separate writable data, relocation state, TLS and module handles.

The system its goals: extreme stability, extreme uptime consistency and reliability, focus on extreme preventive security instead of reactive security (unlike OSs usually do), roughly a priority for 11/10 throughput and 7/10 latency overall, extreme performance, high transparency, extreme consistency, proving you can have better security with the permission system in the filesystem while on single-user instead of multi-user, extreme memory efficiency, complete correctness (extremely rare edge cases aren't left alone because "they're never gonna happen anyways", they are fully eliminated to ensure the system can't have any accidental failures), extreme write amplification minimization, extreme CPU efficiency, high data size compactness, extreme modernism, absolute maximum integrity, full removal of privacy invading services, significant reduction of licensing/agreement policies and low implementation complexity per individual subsystem. FACIOS uses the order "XCDA-256 compression into private memory > place the complete replacement state into the bounded in-memory write batch and publish it as the latest volatile-visible file-data version > when the applicable batch deadline expires write all group journal intents containing previous state, replacement state and affected allocations > flush > write all group new compressed blocks > flush > write all group commit records > flush > durably publish all group replacement metadata > flush > advance the latest durable file-data generations and record completion > reclaim old blocks and journal space" internally. When the memory deduplicator starts a full roundtrip, it records one snapshot of "struct per_cpu_atomic_uint64 memory_change_generation[logical_core_count];". Each logical CPU owns and increments only its own counter for every kernel-observable change performed on that CPU which may affect memory deduplication, including allocations, frees, mapping changes and copy-on-write events; reaching UINT64_MAX before another increment on any CPU causes "RING 0 EXECUTION ERROR" instead of wrapping. The scanner snapshots every per-CPU generation at the start of a full roundtrip and compares the current per-CPU generations against that snapshot while validating the pass and at completion, so no globally shared memory-change counter cache line is required. Ordinary Ring 3 writes to already-writable private pages do not directly increment "memory_change_generation" and are tracked through hardware PTE dirty bits. The memory scanner clears the dirty bit of an eligible mapping only while holding its page-table lock and performs the required TLB invalidation so later writes set it again. A changed per-CPU generation or newly dirty eligible mapping makes the current memory pass outdated and causes the scanner to restart or adapt from the changed state. If a complete memory roundtrip observes neither condition, normal memory deduplication scans pause, but the scanner continues low-frequency dirty-bit checks and resumes normal scanning when a dirty mapping or generation change is detected. This avoids relying on an unobservable user-space write notification while still reducing work during stable periods. FACIOS write syscalls return after the complete replacement file-data object, changed block-map nodes, compressed replacement blocks, journal intent state and affected allocation state have been accepted into the bounded in-memory write batch and the complete replacement has been published as the latest volatile-visible file-data version; return therefore means that the write has been accepted by FACIOS and is immediately visible to reads but does not yet guarantee that it is durable on the storage device. FACIOS uses 20% of the installed RAM (12 GiB maximum limit on top of that to prevent dynamically chosen insane cache sizes, an intentionally very large maximum for huge I/O throughput) as a read/decompression and private write-preparation/write-batching cache; this capacity is not preallocated/reserved while nothing is in it. FACIOS batches all writes. General writes are flushed to the disk after 15 seconds. The first pending write in each batch starts its corresponding fixed timer and later writes do not extend it. When the total FACIOS cache capacity is reached, FACIOS immediately flushes every pending write batch from oldest to newest until no pending dirty write remains. Before shutdown or reboot, MUDOS_64 rejects new filesystem-modifying operations, immediately starts flushing every pending FACIOS write batch from oldest to newest, waits for every in-flight FACIOS transaction and storage I/O operation to complete, flushes the journal, published metadata and storage-device volatile write caches, records and durably flushes a clean volume state where supported, disables device bus mastering and only then performs shutdown or reboot. Reclaimable read/decompression cache data is discarded rather than written. This project started on the 4th of June 2026. FACIOS uses bounded group commits for writes. Each mounted FACIOS volume maintains one bounded general-write group-commit queue and one bounded foreground-write group-commit queue. Each mounted FACIOS volume also maintains one monotonically ordered transaction stream and one serialized persistent commit engine; the general-write and foreground-write queues are collecting and latency-classification queues only, and at most one commit group per volume may perform journal-intent, replacement-data, commit-record or durable replacement-metadata I/O at a time. The first pending general write starts a maximum 15 seconds batching window and the first pending foreground write starts a maximum 0.5 seconds batching window; neither deadline is extended by later writes. Additional writes arriving before the applicable deadline may join the same group and share journal-intent, replacement-data, commit-record and replacement-metadata flush operations, while each write retains its own transaction ID, previous state, replacement state and independently recoverable journal records. When a selected foreground or immediate-durable transaction depends on an older pending transaction, every required predecessor transaction is promoted into the same commit group, and no later transaction becomes durable before a predecessor on which its previous state, allocation state, directory state or executable-registration state depends. A batch commits earlier when its fixed transaction-count or data-size limit is reached, journal space becomes constrained, the total FACIOS cache capacity is reached, an immediate durable commit is requested or shutdown/reboot begins. Every normal FACIOS write syscall returns after its complete replacement state has been accepted into the applicable bounded queue and published as the latest volatile-visible file-data version and does not wait for durable storage completion. An immediate durable commit request remains blocked until the batch containing its transaction and every required predecessor has durably committed and its replacement metadata has been durably flushed. When the cache capacity is reached, every pending batch across all mounted FACIOS volumes is committed from oldest to newest until no pending dirty write remains. FACIOS maintains one bounded pair of group-commit queues per mounted FACIOS volume. Opening a folder will launch File_Manager already in the folder's directory. The system uses a memory priority model with Below_Normal = 1, Normal = 2, Elevated = 3 and System_Memory = 4 as memory priority weights. Memory priority applies to reclaim preference for process mappings, page objects, caches and shared-memory objects and does not directly control CPU-cache residency. It influences reclaimable memory objects, allocation-pressure policy and anonymous-page paging order. The default for all program mappings and page objects is memory priority Normal and the user can set an important program its mappings and page objects to memory priority Elevated, but memory priority System_Memory is not user selectable. All mappings and page objects of the "System" process are fixed to System_Memory except for the FACIOS clean read/decompression cache, compression workspace and write-preparation workspace. Lowest PID and then lowest virtual address or object ID wins tie-breaking. MUDOS_64 uses dynamic disk-backed paging for anonymous virtual memory without using a paging file, swap file, pagefile or dedicated swap partition. Disk paging is implemented as direct cooperation between the virtual-memory subsystem, the FACIOS physical-block allocator and the applicable block-storage driver. Paging data is not represented as a normal VFS file, does not have a filename, directory entry, mudos_entry_handle, creator_application_id, permission_tier, timestamps or ordinary file metadata and cannot be opened, read, written, renamed, moved, copied, enumerated or deleted through normal .MEXE, .ROOT or filesystem syscalls. FACIOS instead defines paging storage as its own internal allocation class, conceptually "FACIOS_ALLOCATION_PAGING", which identifies physical FACIOS allocation units temporarily owned by the virtual-memory subsystem. FACIOS remains authoritative over disk-space ownership so a paging block can never simultaneously be considered free or belong to a persistent filesystem object, but paging blocks bypass normal VFS/file semantics, XCDA-256 file compression, the normal FACIOS 20% RAM read/decompression and write-preparation/write-batching cache, ordinary file group-commit batching and ordinary persistent-file journal transactions. Disk paging uses the same 4 KiB base granularity as MUDOS_64 virtual-memory pages through a dedicated 4 KiB FACIOS paging allocation granularity instead of the default 16 KiB FACIOS block size. One ordinary anonymous 4 KiB page is therefore stored as one raw 4 KiB paging allocation whenever possible. Paging data is intentionally stored raw rather than through XCDA-256 so page-out and page-in latency remains bounded and predictable and paging does not consume additional RAM for compression workspaces or temporary compressed representations. Paging I/O also does not enter the normal FACIOS 20% RAM cache because disk paging exists specifically to reclaim physical RAM and must never create a second cached RAM copy of a page merely to move that page out of RAM. FACIOS paging metadata may use small permanently required kernel-owned structures, but the contents of paged-out user memory themselves are never retained in the ordinary FACIOS cache. Paging space is fully elastic. There is no configured minimum or maximum paging-file size. Every writable FACIOS volume may contribute otherwise-unused physical blocks to the paging pool, and the maximum usable paging capacity dynamically grows and shrinks with the volume's currently available space. Persistent filesystem data always has higher allocation priority than revocable paging allocations. FACIOS permanently excludes from paging a bounded forward-progress reserve sufficient for journal operation, commit records, allocation metadata, replacement metadata, paging metadata, recovery operations and any other filesystem operation required to safely free or reassign paging blocks. Paging is never allowed to consume this reserve. The exact reserve size is derived from FACIOS's maximum bounded forward-progress requirement and is not exposed as ordinary usable free space. The virtual-memory subsystem distinguishes at minimum three backing states for anonymous pages: RAM_ONLY, SWAP_ONLY and RAM_AND_SWAP_CLEAN. RAM_ONLY means the authoritative contents exist only in physical memory. SWAP_ONLY means the authoritative contents exist only in a valid FACIOS paging allocation and no physical RAM copy is currently resident. RAM_AND_SWAP_CLEAN means the page is resident in RAM and an identical valid paging copy also exists on disk. When a RAM_AND_SWAP_CLEAN page is modified, the old paging copy becomes stale and is released or marked reusable, and the page returns to RAM_ONLY state. When disk space is required, RAM_AND_SWAP_CLEAN paging allocations are the first paging allocations that may be discarded because their contents already remain valid in RAM and releasing their disk blocks loses no information. A normal page-out begins only after the virtual-memory subsystem has selected an eligible anonymous RAM page for reclamation. The source physical page remains allocated, mapped or otherwise retained and is pinned against reuse while paging I/O is outstanding. The virtual-memory subsystem requests one or more FACIOS_ALLOCATION_PAGING blocks from the applicable volume, builds a paging entry describing the exact volume identity, volume instance, paging allocation location and paging generation, and submits a raw storage write. The storage driver may DMA directly from the physical page being evicted where the hardware and IOMMU mapping permit this, avoiding a second temporary 4 KiB copy. The source physical page is not released and the process page-table entry is not converted to disk-backed state until the complete paging write has completed successfully. After successful completion, the paging entry is published, the corresponding user mapping is changed to a non-present paging-backed representation under the applicable page-table lock, the required TLB invalidation is completed, and only then may the former physical page be returned to the physical-memory allocator. If the paging allocation fails, the storage write fails, the device disappears, an IOMMU fault occurs, or any other error prevents establishment of valid backing, the original physical page remains authoritative and may not be discarded. A page fault on a SWAP_ONLY page allocates a destination physical page and submits a raw read from the exact paging allocation described by the page's paging entry. The destination physical page remains private to the fault operation until the read has completed successfully. The storage driver may DMA directly into the destination physical page. After successful completion, the virtual-memory subsystem validates that the paging entry, process, page object and mapping generation still refer to the expected page, installs the destination page into the process page tables, performs the required TLB synchronization and wakes the blocked faulting thread. The paging allocation may then either be retained as an identical clean backing copy, producing RAM_AND_SWAP_CLEAN state, or released immediately according to current disk-pressure and paging policy. A failed page-in does not expose partially read data as a valid page and is handled as a fatal memory-access failure for the affected process unless the failure is part of a wider unrecoverable system or storage condition requiring kernel-level failure handling. Persistent filesystem allocation pressure may cause the paging pool to contract dynamically. When FACIOS cannot satisfy a persistent allocation request from ordinary free blocks while preserving its mandatory forward-progress reserve, it requests paging-space reclamation from the virtual-memory subsystem before returning insufficient-disk-space failure. Paging reclamation first releases paging allocations belonging to RAM_AND_SWAP_CLEAN pages because these blocks can be discarded without performing any page-in. Paging allocations belonging to terminated processes, destroyed page objects, invalidated mappings or obsolete paging generations are likewise immediately reclaimable. A SWAP_ONLY paging allocation cannot simply be discarded because it contains the only authoritative copy of that anonymous memory. Such an allocation may be released only after the virtual-memory subsystem has successfully restored the page into physical RAM or has otherwise established another authoritative backing location. Disk-pressure reclamation of a SWAP_ONLY page therefore performs the reverse of ordinary paging. The virtual-memory subsystem allocates a physical page, reads the paging allocation into it, validates successful completion, publishes the physical page as the authoritative resident copy and only then releases the corresponding FACIOS paging allocation. If insufficient physical RAM is available to restore enough SWAP_ONLY pages, those paging allocations remain temporarily required and FACIOS may not reclaim them. Consequently, the total number of disk blocks occupied by paging is not always equal to the number of blocks immediately reclaimable for persistent filesystem writes. MUDOS_64 tracks this distinction explicitly, including at minimum currently allocated paging blocks, paging blocks immediately reclaimable without data movement and paging blocks currently required because they are the sole backing of live anonymous memory. A persistent filesystem write which requires additional disk capacity may therefore reclaim paging space only to the extent that doing so is safe. If all ordinary free blocks and immediately reclaimable paging blocks are exhausted and remaining SWAP_ONLY pages cannot be restored to RAM without violating memory-allocation or forward-progress guarantees, the persistent write is rejected with the normal insufficient-disk-space result rather than destroying live process memory. Disk paging never grants the filesystem permission to discard an authoritative anonymous page merely because a user or application requests more persistent storage. Memory pressure and disk pressure therefore operate in opposite directions. Under RAM pressure, eligible RAM_ONLY anonymous pages may move from physical memory into FACIOS paging allocations and become SWAP_ONLY. Under disk pressure, reclaimable paging allocations are released and, when necessary and possible, SWAP_ONLY pages are moved back into physical RAM so their disk allocations can be returned to FACIOS. No fixed swap size, resize operation, pagefile preallocation or swap partition management is required. Paging capacity automatically expands into otherwise-unused FACIOS space and contracts as persistent storage requirements increase. Disk paging does not use normal FACIOS durability semantics because anonymous process memory is not persistent across system boots. Page-out correctness requires only that a paging write complete successfully before its RAM copy is released. Paging writes are therefore not passed through ordinary FACIOS file group-commit queues and do not perform the normal journal-intent > flush > replacement-data > flush > commit-record > flush > replacement-metadata > flush sequence. Paging I/O is submitted directly through the storage-I/O path after FACIOS has safely assigned the corresponding paging blocks. Storage barriers required for device correctness, DMA ownership or ordering of paging metadata may still be used where necessary, but paging does not request persistent crash-recoverable file semantics. Every system boot establishes a new non-zero paging-session generation. All paging allocations belong to the paging session in which they were created. Paging-session generation values never silently wrap; exhaustion is treated as a RING 0 EXECUTION ERROR. Because running processes and anonymous memory are not restored across reboot, shutdown failure or power loss, paging allocations belonging to an earlier paging session contain no live state. During mount or paging-pool initialization, FACIOS may therefore reclaim all paging allocations whose paging-session generation does not match the current boot after validating that those allocations are not part of persistent filesystem state. Clean shutdown may proactively release paging allocations, but system correctness does not depend on doing so before power loss. Paging allocation metadata is kernel-internal and is never trusted from executable input or ordinary filesystem data. A paging reference must contain enough identity information to prevent stale disk-space reuse from making an old page-table entry refer to a newer unrelated paging allocation. At minimum, the reference contains the applicable volume identity, volume_instance_id, physical paging block or internal paging-allocation identifier and a non-zero paging generation. Reuse of a paging-allocation identifier changes its generation. A stale paging reference is rejected rather than interpreted as valid memory backing. Paging-generation wrap is a RING 0 EXECUTION ERROR. Paging metadata and page-table transitions are synchronized with the existing MUDOS_64 page-table locks, memory-object lifetime rules, TLB-generation system and per-CPU TLB shootdown mechanism. A mapping cannot simultaneously be treated as resident and non-resident by different CPUs. Publishing SWAP_ONLY state occurs only after the backing write is valid, and publishing RAM-resident state during page-in occurs only after the complete destination page is valid. Threads faulting on a page already undergoing page-in wait on the same page-in operation rather than issuing duplicate reads. Similarly, concurrent page-out, unmap, process termination, copy-on-write, deduplication and disk-pressure reclamation operations must resolve ownership of the affected page object before changing backing state. Pages which are not anonymous do not require disk paging merely because they are reclaimable. A clean file-backed page may normally be discarded and reconstructed later from its original persistent file rather than written into paging space. Dirty private copy-on-write pages and other anonymous-derived memory use the paging system when their contents cannot otherwise be reconstructed. Shared-memory objects use paging only according to their own lifetime and visibility rules, and a shared page may not be discarded while any live object still requires its contents. Kernel memory marked permanently required or System_Memory is not paged unless a separate subsystem explicitly defines such support; the initial MUDOS_64 disk-paging implementation primarily targets reclaimable Ring 3 anonymous memory. Memory priority participates in paging selection. Below_Normal mappings are preferred for page-out before Normal mappings, Normal mappings before Elevated mappings, and System_Memory is excluded from ordinary anonymous paging. Memory priority changes reclaim preference and does not make a page immune to mandatory correctness operations. Within equal priority, deterministic tie-breaking is used according to the existing MUDOS_64 memory-management policy. The paging subsystem may also consider recent access information and hardware page-table accessed/dirty state so actively used pages are less likely to be selected than cold pages, but paging decisions must remain bounded and must not require unstable runtime benchmarking. The paging subsystem is integrated with MUDOS_64 OOM handling. Physical-memory pressure first performs normal reclamation of disposable caches and clean reconstructible pages before paging anonymous pages where appropriate. Paging is attempted only when a usable writable FACIOS paging pool exists and the required storage operation can make forward progress. Disk paging is not treated as infinite memory. If physical memory, reclaimable caches and safely usable paging capacity are all exhausted, allocation follows the existing MUDOS_64 OOM rules rather than overcommitting memory without backing. Likewise, a storage failure that permanently removes the only backing of live SWAP_ONLY pages is considered a severe memory-integrity failure affecting the owning processes and may escalate when required for system forward progress. Task Manager reports physical memory and virtual-memory usage separately. Virtual-memory statistics include disk-backed anonymous paging capacity and current paging occupancy rather than pretending paging blocks are physical RAM. FACIOS/free-space accounting may separately report persistent-data capacity, ordinary immediately free space and internal paging occupancy so internal accounting remains exact. User-facing File Manager free-space presentation may present a simplified usable-capacity value, but the allocator itself always distinguishes actually free blocks, immediately reclaimable paging blocks, required SWAP_ONLY backing and the mandatory FACIOS forward-progress reserve. The resulting MUDOS_64 paging path is therefore "anonymous physical page > VM selects page > FACIOS assigns internal raw paging block > storage driver writes directly from the pinned physical page > successful completion > publish paging entry and non-present page-table state > release physical page" for page-out, and "page fault > allocate physical page > storage driver reads paging block directly into the destination physical page > successful completion and validation > publish resident page-table state > optionally retain the unchanged paging block as RAM_AND_SWAP_CLEAN backing > resume thread" for page-in. Persistent filesystem pressure may reclaim RAM_AND_SWAP_CLEAN paging blocks immediately and may reclaim SWAP_ONLY paging blocks only after their contents have first been restored to RAM or otherwise preserved. This provides dynamic use of otherwise-free disk capacity without a paging file, avoids routing paging through the FACIOS 20% RAM cache, avoids unnecessary VFS and file metadata overhead, prevents user-space access to paging contents, preserves complete memory correctness under both RAM and disk pressure and keeps persistent FACIOS storage authoritative over physical disk-space ownership. MUDOS_64 implements vendor-neutral heterogeneous CPU scheduling through a numerical CPU-capacity abstraction instead of hardcoded P-core, E-core, Performance, Efficiency, Big, Little, Mid or other core-type classifications. Every online physical CPU core receives one relative maximum-performance capacity_score using "#define MUDOS_CPU_CAPACITY_SCALE 2048U", where the most capable online physical core or cores are always normalized to exactly 2048, a core with approximately half of that maximum capability is represented near 1024, and lower or intermediate core classes may occupy any value between them. capacity_score == 0 means that the core has no valid schedulable capacity and is never used as an online scheduling destination; every normally schedulable online physical core therefore has a capacity score from 1 through 2048. The score represents relative maximum general-purpose processing capability, not current clock frequency, energy efficiency, thread priority or a guarantee that every workload executes in exactly that performance ratio. No fixed number of heterogeneous classes exists, so a processor containing two, three, four or more performance tiers is represented naturally through different numerical scores without changing scheduler policy. CPU-capacity discovery is vendor-neutral at the scheduler interface and uses a standardized-first backend hierarchy below that interface. The generic scheduler sees only topology and normalized capacity_score values and contains no Intel-specific, AMD-specific, P-core-specific or E-core-specific placement rules. MUDOS_64 first uses standardized architectural or firmware performance-capability interfaces when they provide reliable values documented as comparable across the online physical cores in the current processor, including ACPI CPPC Highest Performance. If no suitable standardized source exists, an architecture-specific or vendor-specific capability mechanism may provide an equivalent raw maximum-performance value, including Intel HWP Highest Performance when its performance units are valid and comparable across the processor. Additional x86_64 vendors or future processor mechanisms may provide another discovery backend without changing the generic scheduler, capacity normalization or placement policy. Vendor mechanisms are therefore allowed to discover physical capability, but vendor-specific thread-placement policy is not imported into the scheduler. Intel Thread Director task classification, AMD vendor task-placement policy, vendor preferred-core scheduling policy and named vendor core classes are not scheduler-visible concepts. For every online physical core, discovery produces a non-zero raw_capacity. SMT siblings belong to the same physical core and share that physical core's capacity value; their reported capability values are validated as belonging to the same physical-core topology object before normalization. After every usable physical core has been discovered, MUDOS_64 finds maximum_raw_capacity, the greatest reliable raw capacity of any online physical core, and calculates "capacity_score = (raw_capacity * MUDOS_CPU_CAPACITY_SCALE + maximum_raw_capacity / 2) / maximum_raw_capacity;" using a sufficiently wide checked intermediate so multiplication cannot overflow. The result is clamped to 1 through 2048 for an online schedulable core, and every core whose raw_capacity == maximum_raw_capacity receives exactly 2048. Equal raw capacities therefore receive equal normalized scores. The numerical scale is system-relative: a score of 1400 on one machine need not describe the same absolute throughput as 1400 on another machine. Raw values from different discovery mechanisms are never mixed merely because their numerical ranges appear similar; one complete mutually comparable source must cover the relevant online processor topology, or the capacity relation is treated as unreliable. MUDOS_64 does not run a CPU microbenchmark during startup to create capacity scores. Cache state, thermal state, boost behaviour, memory performance, power limits, SMT activity and workload choice would make benchmark-derived boot-time capacities non-deterministic and workload-dependent. When no reliable architecture-provided or firmware-provided capacity source is available, when the available values cannot safely be compared across all online physical cores, or when capability discovery is internally inconsistent, MUDOS_64 falls back to homogeneous scheduling by assigning every online physical core capacity_score = 2048. It is preferable to lose heterogeneous-placement optimization than to invent an unreliable capacity hierarchy. The capacity score describes a physical core rather than additive SMT-thread capacity. Every logical CPU belonging to a physical core references that core's capacity_score, but two SMT siblings with a score of 2048 do not imply that their shared physical core has a combined capacity of 4096. MUDOS_64 continues to prefer an independent runnable-idle physical core before placing additional runnable work onto an SMT sibling of an already-active physical core. Physical-core placement calculations aggregate the runnable effective Weight of all logical CPUs belonging to that physical core and divide that aggregate demand by the physical core's single capacity score. SMT therefore increases the number of execution contexts available to the scheduler without being falsely modeled as doubling the core's physical execution capacity. For heterogeneous load comparison, MUDOS_64 defines the capacity-normalized runnable load of one physical core conceptually as "normalized_runnable_load = physical_core_total_runnable_effective_weight * MUDOS_CPU_CAPACITY_SCALE / physical_core_capacity_score;", where physical_core_total_runnable_effective_weight is the sum of the effective Weight of every THREAD_RUNNING and THREAD_READY thread assigned to every online logical CPU belonging to that physical core. A Weight_Normal load of 1000 on a capacity-2048 core therefore contributes a normalized load of 1000, while the same runnable Weight on a capacity-1024 core contributes a normalized load of 2000. Scheduler implementations compare these ratios through checked cross-multiplication where practical instead of requiring division in every candidate comparison. A newly created or newly awakened runnable thread first obeys the existing physical-topology rule that an independent runnable-idle physical core is preferred over an SMT sibling of an already-active physical core. Among otherwise usable physical-core candidates, the scheduler calculates the projected capacity-normalized load after adding the thread's effective Weight and chooses the physical core with the lowest projected normalized load. This naturally gives stronger cores proportionally more runnable work without encoding a fixed core class. After the destination physical core has been selected, an idle logical CPU of that physical core is preferred; otherwise the online SMT sibling with the lowest local total runnable effective Weight is selected. Equal projected normalized load is broken by retaining the thread's current or locality-origin CPU when applicable, then by shared last-level-cache locality, then processor-package locality and finally lowest logical CPU ID. Consequently, under low system load a high-capacity physical core is normally selected before an otherwise equivalent lower-capacity core because adding the same thread produces a lower normalized load on the stronger core. As load increases, lower-capacity cores automatically become useful scheduling destinations when placing more work on the stronger cores would produce a greater projected normalized load. A processor with capacities such as "2048, 2048, 1710, 1710, 1230, 1230, 760, 760" therefore requires no special distinction between four theoretical core classes; the same placement algorithm operates directly on the numerical capacities. The existing ordinary runnable-Weight load-balancing policy becomes capacity-aware on heterogeneous systems. The 20% migration arm threshold, 15% disarm threshold and 32ms per-thread migration cooldown remain unchanged, but the imbalance comparison is performed using capacity-normalized physical-core runnable load rather than unscaled runnable Weight when different-capacity physical cores are compared. A physical core is considered sufficiently more loaded than another for ordinary load-balancing purposes when its normalized runnable load exceeds the destination's normalized runnable load by the existing armed threshold. The hysteresis remains armed until the normalized difference falls below the existing 15% disarm threshold. When physical cores have equal capacity, this reduces exactly to the previous runnable-effective-Weight behaviour. Capacity-preference migration is a separate migration trigger from ordinary 20%/15% load balancing and from existing topology-spread migration. When a higher-capacity physical core becomes runnable-idle while a lower-capacity physical core contains runnable work, MUDOS_64 may move a suitable thread to the stronger runnable-idle physical core even when the ordinary source-more-than-one-runnable-thread requirement or 20% load-imbalance threshold is not satisfied. This prevents a single long-running thread from remaining indefinitely on a weaker core while a stronger independent core is unused. Capacity-preference migration uses the same 32ms per-thread migration cooldown and never overrides the rule that an independent physical core is preferred before an additional SMT sibling. When more than one thread can satisfy a capacity-preference migration, a THREAD_READY thread is preferred over unnecessarily preempting a THREAD_RUNNING thread. Among otherwise equivalent candidates, higher effective Weight is preferred, then shorter effective Latency Class, then deterministic PID/TID ordering. EEVDF eligibility does not prohibit migration because an ineligible THREAD_READY thread remains runnable and its existing EEVDF service state can be preserved across migration. If a THREAD_RUNNING thread must be migrated, another CPU never directly changes the remotely executing thread's state; the owning logical CPU receives the migration request, accounts current attributable runtime, performs the required reschedule, revalidates the destination and cooldown and then performs the normal THREAD_RUNNING > THREAD_READY > THREAD_MIGRATING transition before transfer. Existing topology-spread migration remains logically separate. If multiple SMT siblings of one physical core contain runnable work while another independent physical core is runnable-idle, topology spreading may occur regardless of the ordinary 20%/15% capacity-normalized load threshold. When multiple runnable-idle destination physical cores can satisfy topology spreading, projected capacity-normalized load is used to select between them after the requirement to use an independent physical core has been established. Existing runqueue-lock ordering, destination reservation, migration cooldown, THREAD_READY/THREAD_MIGRATING state rules, blocking-state rules and normalized EEVDF service-lag reconstruction remain unchanged. CPU capacity does not modify EEVDF Weight, Latency Class, task_virtual_runtime, request size or virtual-deadline arithmetic. Weight remains a proportional CPU-service entitlement and Latency Class remains the physical request-length and latency control. Capacity is a property of the execution resource and affects only topology-aware placement, capacity-aware load comparison and migration decisions. A Weight_Normal thread does not become a higher-Weight thread merely because it executes on a slower core, and execution already received on one core is never retroactively scaled when the thread migrates to another capacity class. The existing normalized service-lag migration mechanism continues to preserve scheduling fairness between per-CPU virtual-time domains. Current P-state or instantaneous frequency is also not written directly into capacity_score. A core whose maximum score is 2048 remains a capacity-2048 core while temporarily downclocked or idle because power-management state and maximum architectural capability are separate concepts. Frequency and idle-state control remain the responsibility of Drivers.c its Power Management section. Hardware-delivered-performance counters may be used by power management or future utilization-invariance logic, but a temporary low frequency does not permanently demote a core's topology capacity. When a supported hardware capability mechanism explicitly reports that a core's maximum performance capability has changed, MUDOS_64 may reread the affected raw capacities, construct a complete new capacity table, normalize the complete online set again against a maximum of 2048 and publish the new table as one scheduler-topology generation. The scheduler never observes a mixture of old and new capacity generations. After publication, placement and load-balancing state is reevaluated and future migrations use the new capacities. Temporary thermal or energy-efficiency rankings which do not represent a change in maximum general-purpose core capability are not silently substituted for the static capacity_score. Manual overclocking is handled conservatively. SMT siblings of one physical core must use the same override. With no override, the selected reliable architecture-provided or firmware-provided value remains authoritative. Capacity values are stored in the CPU-topology data used by Scheduler.c its CPU Topology/Placement, Load Balancing and Migration sections. Standardized and vendor-specific capability discovery code belongs below this abstraction in the applicable x86_64 CPU, ACPI or power-management discovery path. MUDOS_64 therefore remains scheduler-vendor-neutral while supporting arbitrary heterogeneous x86_64 CPU layouts through the single normalized 1-through-2048 maximum-capacity scale. The native NVMe driver is a Ring 0 PCIe block-storage driver implemented directly in "Drivers.c" and does not use UEFI storage services after ExitBootServices(). It supports ordinary NVMe NVM block namespaces only and intentionally implements the minimum command/transport subset required for high-performance general-purpose storage: controller initialization/reset, Identify Controller, Identify Namespace, Set Features(Number of Queues), Create/Delete I/O Completion Queue, Create/Delete I/O Submission Queue, Read, Write and Flush. Zoned Namespaces, Key Value, Computational Programs, NVMe over Fabrics, NVMe over TCP/RDMA, vendor-specific commands, Controller Memory Buffer, Persistent Memory Region, Host Memory Buffer, SR-IOV, SGL data transfer and other optional NVMe functionality are unsupported unless added later. The driver supports multiple independent NVMe controllers and multiple ordinary NVM namespaces per controller, with every usable namespace exposed to the storage/VFS layer as an independent block device. NVMe controllers are discovered through the PCI/PCIe layer. The driver maps the controller MMIO register BAR as uncacheable/device memory and validates the controller capability/version/register state before enabling bus mastering. It reads CAP to determine at minimum maximum queue entries, required queue contiguity, timeout, doorbell stride, supported command sets and supported host memory page sizes. MUDOS_64 uses only a 4 KiB NVMe host memory page size; a controller whose supported MPSMIN/MPSMAX range does not include 4 KiB is rejected. Controller MMIO accesses use the exact register widths/alignment required by NVMe and the driver uses memory barriers where required so queue-entry memory writes become globally visible before the corresponding Submission Queue doorbell is written and completion-entry reads become visible before queue state is reused. Every DMA-capable NVMe controller is first placed in its own existing VT-d/AMD-Vi protection domain. Bus mastering remains disabled until the controller's IOMMU domain exists and its required queue/DMA mappings have been installed. NVMe queue memory, PRP-list memory and I/O buffers accessible by the controller use MEMORY_DMA and are mapped into that controller's DMA domain with only the read/write permissions required for that transfer. Kernel virtual addresses are never placed directly into NVMe commands; PRP addresses contain only the corresponding controller-visible DMA addresses. DMA buffers remain pinned and mapped until the command which references them has completed or the controller has been completely quiesced/reset. Queue/DMA memory is unmapped and released only after bus mastering is disabled and the driver has guaranteed that the controller can no longer access it. Controller initialization uses the normal NVMe disable/configure/enable sequence. CC.EN is cleared when required and the driver waits for CSTS.RDY to become 0 within the controller-defined timeout. The Admin Submission Queue and Admin Completion Queue are allocated as zeroed, 4 KiB-aligned, physically contiguous DMA memory, AQA/ASQ/ACQ are programmed, CC is configured for the NVM Command Set with 64-byte Submission Queue entries, 16-byte Completion Queue entries and a 4 KiB host memory page size, then CC.EN is set and the driver waits for CSTS.RDY to become 1 within the controller-defined timeout. CSTS.CFS or an initialization timeout makes that controller unavailable instead of continuing with an uncertain controller state. Early Admin Queue commands may use bounded polling because the scheduler/interrupt-backed storage path does not need to be involved in controller bring-up. The Admin Queue uses "#define MUDOS_NVME_ADMIN_QUEUE_DEPTH 64U". After Identify Controller, the driver requests the maximum useful number of I/O queue pairs through Set Features(Number of Queues), bounded by the controller's returned limit, the number of logical CPUs and the number of usable interrupt vectors. Each I/O Submission Queue and Completion Queue uses at most "#define MUDOS_NVME_IO_QUEUE_DEPTH 256U" entries, further reduced when CAP.MQES requires a smaller queue. All hardware queue buffers are allocated as physically contiguous 4 KiB-aligned DMA memory so controllers requiring contiguous queues are supported without implementing non-contiguous queue storage. MUDOS_64 creates up to one I/O queue pair per logical CPU. When fewer queue pairs than logical CPUs are available, CPUs are deterministically distributed across the available queues. Each queue's interrupt is given affinity to its corresponding logical CPU where interrupt-routing hardware permits this. MSI-X is the preferred NVMe completion-interrupt mechanism and separate MSI-X vectors are assigned to I/O Completion Queues where available. MSI is the fallback when the controller/platform cannot supply sufficient MSI-X vectors. Legacy PCI INTx is not required by the native NVMe implementation. VT-d/AMD-Vi interrupt remapping is used when supported according to the system-wide PCI DMA/interrupt-remapping rules. An NVMe interrupt handler processes completed entries from the applicable Completion Queue until the next entry's Phase Tag shows that no further completion is available, advances the Completion Queue head, writes its head doorbell, records each command's completion status and makes the completed requests available to the waiting storage/FACIOS paths. Interrupt handlers never perform filesystem compression, journal processing or other unbounded filesystem work. Each I/O queue owns one spinlock protecting its Submission Queue tail, Completion Queue head, Phase Tag state, free Command Identifier slots and outstanding-request table. There is no global NVMe I/O lock. Submission selects one free queue slot/Command Identifier in O(1), writes the complete 64-byte Submission Queue entry, performs the required publication memory barrier, advances the tail and writes the queue's Submission Queue Tail Doorbell. A Command Identifier is never reused until its previous command has produced a valid completion or the complete queue/controller has been reset and detached from all old requests. Completion processing resolves the Command Identifier directly through the queue's fixed outstanding-request table instead of performing an O(n) request search. Controller-management/reset state has a separate per-controller lock and does not serialize normal independent I/O queues. The driver uses PRP data transfer only. PRP1 describes the first data page, PRP2 directly describes the second page when applicable and otherwise references one 4 KiB PRP-list page containing controller-visible DMA addresses for the remaining pages. Chained PRP lists are intentionally not implemented. "#define MUDOS_NVME_MAX_TRANSFER_BYTES 1048576U" therefore provides a simple bounded maximum transfer size of 1 MiB before controller-specific limits are applied. The effective command limit is the minimum of 1 MiB, the controller's advertised maximum data-transfer size when one exists, the namespace/LBA command limit and the amount representable by the driver's single PRP-list page. Larger filesystem/storage operations are automatically divided into multiple NVMe commands without changing the caller-visible operation. This keeps PRP construction bounded while being substantially larger than FACIOS's 256 KiB XCDA-256 frame size. Every identified namespace is validated independently. The initial driver supports ordinary NVM namespaces using 512-byte or 4096-byte logical blocks with no separate metadata and no unsupported protection-information requirement. Unsupported namespace formats are ignored rather than interpreted incorrectly. Namespace size, active LBA format, logical-block size, namespace identifier and relevant controller identity information are retained by the block-device object so a reset/reinitialization cannot silently substitute an incompatible namespace. Read/write requests validate all additions, multiplications, LBA ranges and transfer lengths before creating an NVMe command. Requests extending beyond the namespace capacity are rejected before DMA submission. The NVMe layer exposes asynchronous block Read, Write and Flush operations to FACIOS/VFS with a synchronous wait wrapper where the calling filesystem path requires one. Threads waiting for storage completion do not spin or poll. MUDOS_64 uses THREAD_BLOCK_IO from "enum thread_block_reason" for this wait; THREAD_BLOCK_IO is owned by the storage-I/O subsystem and a thread blocked for I/O remains unschedulable until its request completes, fails, is cancelled during process/system teardown or the owning storage device is removed/reset in a manner which makes that operation impossible. Publishing an I/O completion establishes the completed request state before scheduler_wake_thread() changes an applicable waiter to THREAD_READY, preventing a lost-wakeup window. Asynchronous FACIOS operations may instead retain a request object and continue directly from completion without blocking a thread. NVMe writes are not considered durably stored merely because the corresponding Write command completed. The storage Flush operation is a strict namespace durability barrier used by FACIOS's journal/commit engine. Before issuing an NVMe Flush for a namespace, the driver prevents later writes belonging after that barrier from passing it and waits for every earlier submitted write belonging before that barrier to reach completion. It then submits the namespace Flush command when required by the controller's volatile-write-cache semantics and does not report the durability barrier complete until the Flush command itself has completed successfully. Reads do not need to be globally stopped by a durability barrier. This preserves FACIOS's required ordering of journal intent writes > flush > replacement-data writes > flush > commit records > flush > replacement-metadata writes > flush even when ordinary writes use multiple CPU-local NVMe I/O queues. Normal read/write commands may execute concurrently across every available I/O queue and namespace. FACIOS remains responsible for filesystem ordering, transactions, batching, cache policy, compression and allocation; the NVMe driver knows only block addresses, transfer direction, buffers, completion status and durability barriers. The NVMe driver does not reorder operations across an explicit storage barrier and never converts a failed Flush into a successful completion. Optional NVMe Dataset Management/Deallocate/TRIM support may be added later and is never issued autonomously unless the filesystem explicitly declares the affected physical ranges unused. A command completion whose NVMe status reports failure is converted into a storage-I/O error and propagated upward instead of silently retrying arbitrary writes. Recoverable transient/controller errors may cause one bounded controller-defined recovery/reset attempt when doing so cannot violate filesystem ordering. Controller reset is serialized per controller: new submissions are stopped, interrupts for the old queue instance are quiesced, outstanding requests are completed as failed or retained only where their execution state is unambiguously known, bus mastering/DMA ownership remains valid until the old controller can no longer access those buffers, CC.EN is cleared and CSTS.RDY=0 is awaited, the Admin and I/O queues are rebuilt, and the controller/namespaces are re-identified before normal I/O resumes. A namespace is resumed only when its identity, capacity, active LBA format and logical-block size still match the block device that was mounted before the reset. Ambiguous completed-versus-uncompleted filesystem writes are never guessed to have succeeded; FACIOS durability/recovery rules determine the persistent result. CSTS.CFS, an unrecoverable command timeout, PCIe removal, failed controller reset or permanent DMA/IOMMU fault marks the applicable NVMe controller unavailable and rejects new I/O. Every outstanding request is detached exactly once and completed with failure after the controller can no longer DMA into its buffers. Mounted filesystems are informed that the underlying block device is unavailable; no filesystem continues issuing storage commands to a dead controller. A controller or namespace reappearing later is treated as a newly initialized storage-device instance rather than inheriting stale in-memory requests or stale mounted-volume identity. Before shutdown or reboot, the filesystem layer first stops accepting new modifying operations and performs its normal FACIOS durable commit procedure. The NVMe driver waits for all previously accepted namespace operations, performs every requested Flush durability barrier and confirms completion. It then prevents new NVMe submissions, drains or terminates the I/O queues, disables controller interrupts, disables CC.EN where appropriate and waits for controller shutdown/reset state as required. PCI bus mastering is disabled before IOMMU mappings or DMA buffers are released. Only after the device can no longer DMA are its NVMe queues, PRP lists, interrupt-remapping entries and IOMMU mappings destroyed. This is integrated with the existing system-wide rule that shutdown/reboot completes all filesystem/storage I/O and flushes storage-device volatile write caches before hardware DMA access is removed. MUDOS_64 uses one frozen native Ring 3 API/ABI whose current revision is MUDOS_API_ABI_v1.1, defined entirely through MUDOS_64_API_ABI.h and used by all .MEXE and .ROOT programs. MUDOS_API_ABI_v1.1 is an additive ABI-major-1 extension of v1.0: every v1.0 binary remains valid, while v1.1-aware programs detect the new facilities through MUDOS_API_ABI_MINOR and mudos_abi_features(). Once ABI major version 1 is frozen, every assigned syscall number permanently keeps the same meaning, existing syscall numbers are never renumbered or reused, existing argument meanings never change, existing public structure fields are never removed, reordered or given incompatible meanings, existing enum values are never reused, and future functionality is added only through previously unused syscall numbers, new optional structure versions or new feature bits, except that the explicitly provisional MUDOS_GPU_API_v0 extension occupying syscall range 0x0B00 through 0x0BFF and its GPU-only public types are intentionally excluded from the freeze until that extension is explicitly promoted to a frozen GPU ABI. An application declaring ABI major version 1 therefore remains binary-compatible with later MUDOS_64 versions implementing ABI major version 1 for the frozen non-GPU API; applications using MUDOS_GPU_API_v0 must additionally check its runtime revision and may require recompilation when that provisional GPU extension changes. Unknown or unsupported calls return MUDOS_ERROR_NOT_SUPPORTED. All syscall arguments, user pointers, lengths, offsets, handles, arithmetic and complete memory ranges are validated before being used by Ring 0. All text and filenames exposed by the ABI use UTF-8. All sizes and offsets use uint64_t unless explicitly stated otherwise. Opaque 64-bit handle value 0 is always invalid. Process and thread handles include their instance IDs so PID/TID reuse cannot make a stale handle refer to a newer process or thread. MUDOS_NON_BLOCKING means the syscall must never put the calling thread to sleep and returns MUDOS_ERROR_WOULD_BLOCK when completion would require waiting. MUDOS_BLOCKING permits the syscall to block the calling thread through the appropriate scheduler blocking mechanism until the operation completes, fails, times out or the process terminates. No ordinary syscall exposes kernel pointers, physical addresses, page tables, CR3, hardware PCIDs, TLB invalidation, I/O ports, MSRs, raw interrupt registration, PCI BAR mappings, arbitrary DMA mappings, IOMMU manipulation, kernel spinlocks, scheduler runqueues, FACIOS journal internals, direct-user-action fabrication or arbitrary cross-process memory access. MUDOS_64 reserves 256 syscall numbers for each API subsystem so later ABI-v1 additions can be made without changing existing numbers. The machine-level syscall ABI is permanently fixed for ABI major version 1 on x86-64 and remains byte-for-byte the same as the original MUDOS_API_ABI_v1.0 raw syscall convention. Ring 3 C API functions use the x86-64 System V AMD64 function calling convention and 16-byte stack alignment; this is only the machine calling convention and does not imply POSIX or UNIX compatibility. Every raw kernel transition uses the x86-64 SYSCALL instruction with RAX containing the syscall number and RDI containing a canonical Ring 3 pointer to one 96-byte, 8-byte-aligned "struct mudos_syscall_frame". No syscall arguments are passed on the Ring 3 stack and the raw syscall interface never interprets additional register arguments. "struct mudos_syscall_frame" contains exactly eight 64-bit argument slots followed by four 64-bit structure-result slots. The C wrapper places logical scalar arguments in argument[0] through argument[7] in source-order; unsigned values narrower than 64 bits are zero-extended, signed values narrower than 64 bits are sign-extended, pointer values are stored as their 64-bit canonical user virtual address, and any public structure passed by value is copied into caller-owned temporary ABI memory and the corresponding argument slot contains a pointer to that exact structure instead of flattening it into a slot. Current ABI-v1 syscalls may have at most eight logical arguments; any future ABI-v1 operation requiring more arguments must accept a pointer to a separately defined public argument structure instead of changing the raw frame. The kernel validates the complete syscall frame and every transitively referenced user range before use. A mudos_result_t return is returned in RAX as signed two's-complement int64_t, uint32_t returns are zero-extended in RAX, uint64_t and opaque 64-bit handles return directly in RAX, and void calls return MUDOS_OK in RAX even though the C wrapper discards it. Public structures returned by value are written byte-for-byte into result[0] through result[3] of the syscall frame and RAX returns MUDOS_OK; all currently frozen structure returns fit within these 32 bytes, and a future structure larger than 32 bytes must be returned through an explicit caller-provided output pointer rather than enlarging the frozen frame. The wrapper reconstructs the declared C structure return from those result slots. On raw syscall return RAX, RCX and R11 are clobbered, matching x86-64 SYSCALL/SYSRET requirements, while RBX, RBP, RSI, RDI, RDX, R8, R9, R10, R12, R13, R14, R15 and the exact user RSP are restored to their entry values; the user direction flag is clear on return. RCX contains no preserved application value because SYSCALL uses it for the return RIP and R11 contains no preserved application value because SYSCALL uses it for RFLAGS. All public integer fields and syscall-frame words are little-endian. The raw syscall frame layout is:


struct mudos_syscall_frame
{
    uint64_t argument[8];
    uint64_t result[4];
};

All public MUDOS_API_ABI_v1 structures use only fixed-width integer types, 64-bit pointers where explicitly present, and the field order written in MUDOS_64_API_ABI.h. The ABI uses a maximum structure-member alignment of 8 bytes on x86-64. Structure padding is part of the frozen layout, every kernel-produced padding/reserved byte is zero, and applications must write zero to every reserved input field. Public structures are never compiled with a compiler-dependent C enum field: enum/flag values cross structures only through explicitly sized uint32_t or uint64_t members. Every public enum type appearing directly in a C function signature has a frozen 32-bit ABI representation and MUDOS_64_API_ABI.h rejects a compiler configuration where that enum is not exactly 4 bytes. UTF-8 fixed-size name arrays are NUL-terminated when produced by the kernel, contain at most 256 UTF-8 bytes before the NUL, and any remaining bytes are zero. The already defined struct mudos_application_id and struct mudos_entry_handle are also public ABI types and retain exactly these layouts:

For mudos_ui_event, flags is currently reserved and must be 0. key_code is the USB HID Usage Tables Keyboard/Keypad usage ID from usage page 0x07, making every physical key identity stable without a compiler- or layout-dependent key enum. MUDOS_UI_EVENT_KEY_DOWN and MUDOS_UI_EVENT_KEY_UP use key_code; MUDOS_UI_EVENT_MOUSE_MOVE uses x, y, delta_x and delta_y; MUDOS_UI_EVENT_MOUSE_BUTTON_DOWN and MUDOS_UI_EVENT_MOUSE_BUTTON_UP use mouse_button; MUDOS_UI_EVENT_MOUSE_WHEEL uses wheel_delta; MUDOS_UI_EVENT_RESIZE uses width and height; and MUDOS_UI_EVENT_CONTEXT_MENU_SELECTION uses context_menu_item_id. Fields not used by an event type are zero. mouse_button uses enum mudos_mouse_button. utilization_x100 and fragmentation_x100 are hundredths of one percent in the inclusive range 0 through 10000. Every mudos_system_query output begins with struct mudos_query_header where size is the exact byte size of the returned structure and version is 1 for the structures frozen above. For MUDOS_QUERY_CPU, MUDOS_QUERY_GPU, MUDOS_QUERY_STORAGE, MUDOS_QUERY_NETWORK and MUDOS_QUERY_AUDIO, the syscall index argument selects the zero-based object index. For MUDOS_QUERY_SYSTEM, MUDOS_QUERY_MEMORY and MUDOS_QUERY_SCHEDULER, index must be 0. struct mudos_ipv4_address stores the IPv4 address in network byte order. The exact ABI-v1 sizeof values are: mudos_application_id=32, mudos_entry_handle=32, mudos_process_handle=16, thread_handle=16, mudos_startup_info=72, mudos_process_info=376, mudos_thread_info=72, mudos_process_exit_info=32, mudos_wait_item=32, mudos_wait_result=32, mudos_completion_record=24, mudos_module_symbol=24, mudos_module_info=360, mudos_ipc_message=120, mudos_memory_info=32, mudos_directory_entry=320, mudos_entry_info=384, mudos_volume_info=328, mudos_ui_surface=32, mudos_ui_rect=16, mudos_ui_event=64, mudos_text_measurement=16, mudos_context_menu_item=272, mudos_audio_format=32, mudos_audio_device_info=312, mudos_datetime=32, mudos_ipv4_address=4, mudos_network_info=296, mudos_query_header=8, mudos_query_system_info=32, mudos_query_cpu_info=40, mudos_query_memory_info=48, mudos_query_scheduler_info=40, mudos_query_gpu_info=32, mudos_query_storage_info=40, mudos_query_network_info=32 and mudos_query_audio_info=32 bytes. MUDOS_64_API_ABI.h uses compile-time sizeof and offsetof assertions for all of these layouts so an incompatible compiler/build fails instead of silently producing a different ABI. The public block_reason field in struct mudos_thread_info uses the exact numeric THREAD_BLOCK_* values from enum thread_block_reason: NONE=0, SLEEP=1, MUTEX=2, IPC=3, IO=4, EVENT=5, THREAD=6, UI=7, AUDIO=8, NETWORK=9, GPU=10, PROCESS=11, PIPE=12, WAIT_MANY=13 and COMPLETION=14.


MUDOS_GPU_API_v0 is an explicitly provisional accelerated graphics/compute extension inside MUDOS_64_API_ABI.h. It is available to .MEXE and .ROOT programs now when MUDOS_FEATURE_GPU_ACCELERATION is reported, but its GPU-only syscall signatures, structures, enum values and semantics are not frozen and may be revised while the extension remains version 0. The frozen structure-size/offset list above intentionally does not include the provisional GPU-only structures below. Every application using the GPU extension must call mudos_gpu_api_revision() and require a revision it understands before using any other 0x0Bxx call. The current provisional revision is:

MUDOS_GPU_API_v0 is hardware-neutral at the application boundary. Ring 3 never receives GPU MMIO addresses, PCI BAR mappings, physical VRAM addresses, raw DMA addresses, native AMD/Intel command packets or privileged hardware state. The driver owns device initialization, GPU page tables/address spaces, VRAM/GTT allocation, command-stream construction, cache management, interrupt handling, fault handling and hardware scheduling. Every process gets isolated GPU resource ownership and an isolated GPU virtual-address context where supported by the hardware; one process cannot bind, map, submit or present another process its GPU objects. Memory which can become visible to a different process is zeroed before reuse. GPU buffer/image sizes, offsets, formats, binding ranges, draw/dispatch dimensions and every arithmetic calculation are validated before hardware submission. CPU-visible GPU buffers are mapped only into their owning Ring 3 process; mudos_gpu_buffer_map() and mudos_gpu_buffer_unmap() perform the required CPU/GPU cache maintenance for the selected hardware so applications do not issue vendor-specific cache commands. Device-local resources which are not CPU-visible are populated/read back through transfer commands using CPU-visible staging buffers.


Shaders are supplied as validated SPIR-V binary modules using 32-bit little-endian words. Revision 1 supports vertex, fragment and compute stages. Only instructions, capabilities, numeric types, storage classes and resource accesses supported by the selected device and this API revision are accepted. The GPU driver validates the complete module, entry point, declared resource interface and bounds-relevant metadata before compiling it to the selected hardware's native instruction set; Ring 3 cannot submit arbitrary native GPU ISA. Shader compilation failure returns MUDOS_ERROR_NOT_SUPPORTED or MUDOS_ERROR_INVALID_ARGUMENT rather than executing unvalidated code. Graphics pipelines combine one vertex and one fragment shader; compute pipelines use one compute shader. Tessellation, geometry, mesh/task shaders, ray tracing and vendor-specific shader extensions are not part of provisional revision 1 and may be added later while MUDOS_GPU_API_v0 remains provisional.


Resource binding uses one flat binding namespace numbered 0 through MUDOS_GPU_MAX_BINDINGS-1. SPIR-V modules used by provisional revision 1 must use DescriptorSet=0 and their Binding decoration maps directly to this flat MUDOS binding number; any other descriptor set is rejected. Uniform buffers, storage buffers, sampled images and storage images are bound through struct mudos_gpu_binding. For MUDOS_GPU_BINDING_SAMPLED_IMAGE, resource is a mudos_gpu_image_t and auxiliary is the required mudos_gpu_sampler_t; for storage images auxiliary is 0; for buffer bindings resource is a mudos_gpu_buffer_t, auxiliary is 0 and offset/size select the visible validated range. Push-constant data is copied into the command buffer when recorded and may not exceed the selected device's max_push_constant_bytes or MUDOS_GPU_MAX_PUSH_CONSTANT_BYTES. Command buffers record validated hardware-neutral operations. A command buffer must be reset, begun, recorded and ended before submission, may be submitted only to the device which created it and may not be modified while an outstanding submission still references it. The initial implementation uses one logically ordered graphics/compute/transfer submission stream per opened device. This intentionally avoids exposing vendor queue-family details in revision 1; independent command buffers can still be recorded from multiple CPU threads, while submissions execute in API order. Resource barriers explicitly declare state transitions needed between transfer, shader, attachment, vertex/index/uniform/indirect and presentation uses. The driver converts these transitions into the required RDNA/Intel cache, synchronization and layout operations.


Swapchains connect accelerated rendering directly to caller-owned MUDOS windows. The swapchain owns its presentation images; mudos_gpu_swapchain_get_image() returns borrowed image handles which are valid only until that swapchain is destroyed/recreated and applications must not destroy them directly. MUDOS_GPU_PRESENT_FIFO waits for the normal display presentation cadence and does not intentionally tear, while MUDOS_GPU_PRESENT_IMMEDIATE may tear. A resize event requires the application to stop using the old swapchain after outstanding work completes and create a replacement with the new dimensions. Fence waits block through THREAD_BLOCK_GPU rather than spinning. GPU interrupts publish the applicable completed fence/submission/swapchain state before scheduler_wake_thread() wakes a GPU-blocked thread, preventing lost wakeups. Process exit destroys or invalidates all process-owned GPU objects after outstanding hardware access has been quiesced or the context/device has been safely reset. A shader fault, invalid command state or GPU virtual-memory violation terminates/fails the offending process/context when isolation permits; a device hang or unrecoverable hardware fault triggers bounded device reset, fails all affected outstanding GPU work with MUDOS_ERROR_DEVICE_UNAVAILABLE and never continues using uncertain DMA mappings.


The process/thread handle {0,0} is always invalid. Every other opaque API handle uses value 0 as its invalid value. Syscall range 0x0000 through 0x00FF is reserved for ABI/core functionality. Syscall 0x0000 is "uint32_t mudos_abi_major(void);" and returns the implemented MUDOS API ABI major version. Syscall 0x0001 is "uint32_t mudos_abi_minor(void);" and returns the implemented ABI minor version. Syscall 0x0002 is "uint64_t mudos_abi_features(void);" and returns a feature-bit mask describing optional facilities available on the current MUDOS_64 installation, such as networking, GPU acceleration, audio input and other optional capabilities. Applications must use this instead of assuming that optional hardware or subsystems are available. Syscall 0x0003 is "mudos_result_t mudos_random_bytes(void *buffer, uint64_t size);" and fills the validated user buffer with cryptographically suitable kernel-provided random data using the system RNG source. It is intended for TLS, Web Crypto, tokens, identifiers and other security-sensitive randomness. Syscall range 0x0100 through 0x01FF is reserved for process and thread management. Syscall 0x0100 is "struct mudos_process_handle mudos_process_self(void);" and returns the exact current process PID and process instance ID. Syscall 0x0101 is "struct thread_handle mudos_thread_self(void);" and returns the calling thread TID and thread instance ID. Syscall 0x0102 is "void mudos_process_exit(int64_t exit_code);" and terminates the calling process through the normal PROCESS_EXITING cleanup path and does not return. Syscall 0x0103 is "struct thread_handle mudos_thread_create(void (*entry)(void), uint64_t stack_size);" and creates a new thread in the calling process using the supplied validated Ring 3 entry point and requested stack limit. This is the frozen form of the previously specified mudos_thread_create functionality. Failure returns the invalid {0,0} handle. Syscall 0x0104 is "void mudos_thread_exit(int64_t exit_code);" and terminates only the calling thread unless normal MUDOS process rules cause the complete process to terminate, such as the exiting thread being the process main thread. Syscall 0x0105 is "void mudos_thread_yield(void);" and voluntarily ends the calling thread's current scheduler request and invokes normal rescheduling without fabricating runtime. Syscall 0x0106 is "mudos_result_t mudos_thread_sleep(uint64_t nanoseconds);" and blocks the caller with THREAD_BLOCK_SLEEP until the absolute scheduler wake deadline corresponding to the requested relative interval has been reached. Syscall 0x0107 is "mudos_result_t mudos_thread_wait(struct thread_handle thread, uint64_t timeout_ns);" and blocks until the specified thread terminates or the timeout expires. A timeout value of UINT64_MAX means no timeout. A .MEXE may wait only on threads belonging to its own process unless a future explicitly authorized mechanism says otherwise. Syscall 0x0108 is "mudos_result_t mudos_thread_get_scheduling(struct thread_handle thread, uint64_t *weight, uint32_t *latency_class);" and returns the current base scheduling Weight and Latency Class for a thread the caller is allowed to inspect. Syscall 0x0109 is "mudos_result_t mudos_thread_set_scheduling(struct thread_handle thread, uint64_t weight, uint32_t latency_class);" and validates the supplied Weight and Latency Class against the frozen MUDOS scheduler enums. A .MEXE may only modify its own threads within the normal policy limits allowed to applications, while ROOT/direct-user-action system management may modify other processes where explicitly authorized. Priority-inheritance values are not directly writable through this API. Syscall 0x010A is "mudos_result_t mudos_process_get_startup_info(struct mudos_startup_info *info);" and returns immutable launch/startup information supplied to the current process, including any entry or directory the shell intentionally opened the program with. Syscall 0x010B is "mudos_result_t mudos_process_get_info(struct mudos_process_handle process, struct mudos_process_info *info);" and returns public process information subject to caller permissions. A .MEXE can always query itself; unrestricted foreign-process inspection is reserved for ROOT/system-management use. Syscall 0x010C is "mudos_result_t mudos_thread_get_info(struct thread_handle thread, struct mudos_thread_info *info);" and returns public thread state/statistics subject to the same ownership/privilege rules. Syscall 0x010D is "mudos_result_t mudos_process_wait(struct mudos_process_handle process, uint64_t timeout_ns, struct mudos_process_exit_info *exit_info);" and waits for an authorized process completion. UINT64_MAX means no timeout and timeout_ns=0 performs a non-blocking completion check. A successful direct-child wait copies the immutable process handle, int64_t exit_status and exit_reason and consumes that parent completion record exactly once; timeout and failure do not consume it. .MEXE callers may wait only on direct children for which they own completion rights, while ROOT/system-management callers require the existing process-management authorization. Syscall 0x0110 is "mudos_result_t mudos_tls_get_base(void **base);" and returns the calling thread's validated user FS/TCB base for runtimes that need it; ordinary compiler static-TLS access uses FS-relative addressing directly and does not call this syscall. Syscall 0x0111 is "mudos_result_t mudos_tss_key_create(mudos_tss_key_t *key);" and allocates one process-local generation-safe TSS key. Syscall 0x0112 is "mudos_result_t mudos_tss_key_destroy(mudos_tss_key_t key);" and invalidates the key generation in O(1); it does not execute user callbacks. Syscall 0x0113 is "mudos_result_t mudos_tss_set(mudos_tss_key_t key, void *value);" and stores one pointer-sized caller value for the current thread. Syscall 0x0114 is "mudos_result_t mudos_tss_get(mudos_tss_key_t key, void **value);" and returns the current thread's value or NULL when the valid key has no value set on that thread. Invalid, stale or foreign TSS keys return MUDOS_ERROR_INVALID_HANDLE; unlike mutex misuse they are not process-fatal because TSS is an ordinary data/runtime facility. Syscall range 0x0200 through 0x02FF is reserved for mutexes, synchronization, IPC and shared pages. Syscall 0x0200 is "mudos_mutex_t mudos_mutex_create(void);". Syscall 0x0201 is "void mudos_mutex_lock(mudos_mutex_t mutex);". Syscall 0x0202 is "void mudos_mutex_unlock(mudos_mutex_t mutex);". Syscall 0x0203 is "void mudos_mutex_destroy(mudos_mutex_t mutex);". These preserve the existing MUDOS_64 generation-safe process-local FIFO mutex design, including priority inheritance and process-fatal handling of invalid/stale/foreign misuse according to the mutex specification. Syscall 0x0204 is "mudos_event_t mudos_event_create(uint32_t initial_state);" and creates a process-local manual-reset event whose initial state is either signaled or unsignaled. Syscall 0x0205 is "void mudos_event_signal(mudos_event_t event);" and atomically changes the event to signaled and wakes applicable waiting threads. Syscall 0x0206 is "void mudos_event_reset(mudos_event_t event);" and changes the event to unsignaled. Syscall 0x0207 is "mudos_result_t mudos_event_wait(mudos_event_t event, uint64_t timeout_ns);" and returns immediately if signaled or otherwise blocks until signal, timeout or process termination. Syscall 0x0208 is "void mudos_event_destroy(mudos_event_t event);" and invalidates and destroys the event after normal reference-safe cleanup. Syscall 0x0210 is "mudos_result_t mudos_ipc_send(struct mudos_process_handle destination, uint32_t message_type, const void *payload, uint32_t payload_size);" and sends one message into the destination process's existing 512-message IPC ring. payload_size may not exceed 96 bytes. Sender PID and sender instance ID are supplied by the kernel and cannot be forged by user space. A full destination queue returns MUDOS_ERROR_QUEUE_FULL. Syscall 0x0211 is "mudos_result_t mudos_ipc_receive(struct mudos_ipc_message *message);" and performs the already specified non-blocking receive from the caller's IPC queue, returning MUDOS_ERROR_WOULD_BLOCK when the queue is empty. Syscall 0x0212 is "void mudos_ipc_wait(void);" and preserves the existing MUDOS_64 IPC wait semantics: it returns immediately when the calling process's queue already contains a message, otherwise atomically publishes the caller into the process FIFO IPC waiter list and blocks it with THREAD_BLOCK_IPC without a lost-wakeup window. After it returns the caller uses mudos_ipc_receive() to consume the message. Syscall 0x0220 is "mudos_shared_page_t mudos_shared_page_create(void);" and creates one zero-initialized 4 KiB reference-counted shared page owned initially by the caller, subject to the existing per-process limit of 64 shared pages/references as applicable. Syscall 0x0221 is "mudos_result_t mudos_shared_page_map(mudos_shared_page_t page, uint32_t permissions, void **address);" and maps the referenced shared page into the caller with validated non-executable user permissions. Syscall 0x0222 is "mudos_result_t mudos_shared_page_unmap(mudos_shared_page_t page);" and removes the caller's current mapping without necessarily releasing the page reference itself. Syscall 0x0223 is "mudos_result_t mudos_shared_page_retain(mudos_shared_page_t page, struct mudos_process_handle destination);" and grants/retains one validated reference for the specified destination process according to the shared-page IPC ownership rules. Syscall 0x0224 is "void mudos_shared_page_release(mudos_shared_page_t page);" and releases one caller-owned reference; the physical shared page is reclaimed only when its global reference count becomes zero. Syscall 0x0230 is "mudos_result_t mudos_wait_many(const struct mudos_wait_item *items, uint32_t item_count, uint64_t timeout_ns, struct mudos_wait_result *result);" and performs the native wait-any operation over 1 through MUDOS_MAX_WAIT_MANY_ITEMS objects. It returns the lowest ready input index when multiple items are ready simultaneously, blocks with THREAD_BLOCK_WAIT_MANY when necessary, never consumes the underlying object state and uses the generation/sequence-safe registration protocol described by the scheduler. Syscall 0x0240 is "mudos_completion_t mudos_completion_create(void);" and creates one empty process-local 256-record completion queue. Syscall 0x0241 is "mudos_result_t mudos_completion_post(mudos_completion_t completion, uint64_t user_tag, int64_t result, uint64_t information);" and atomically appends one complete record or returns MUDOS_ERROR_QUEUE_FULL. Syscall 0x0242 is "mudos_result_t mudos_completion_receive(mudos_completion_t completion, struct mudos_completion_record *record);" and removes the oldest record non-blockingly, returning MUDOS_ERROR_WOULD_BLOCK when empty. Syscall 0x0243 is "mudos_result_t mudos_completion_wait(mudos_completion_t completion, uint64_t timeout_ns);" and blocks until the queue becomes non-empty, timeout occurs or the process terminates. Syscall 0x0244 is "mudos_result_t mudos_completion_destroy(mudos_completion_t completion);" and invalidates the process-local handle after confirming that no in-flight kernel operation owns the object; it returns MUDOS_ERROR_BUSY while an in-flight kernel operation still retains it. Syscall 0x0250 is "mudos_result_t mudos_pipe_create(mudos_pipe_t *read_end, mudos_pipe_t *write_end);" and creates a 65536-byte-capacity lazy-buffered unidirectional byte stream with one read endpoint and one write endpoint. Syscall 0x0251 is "mudos_result_t mudos_pipe_read(mudos_pipe_t read_end, void *buffer, uint64_t size, uint64_t *bytes_read, enum mudos_blocking_mode mode);" and reads bytes in FIFO order with the specified blocking semantics. Syscall 0x0252 is "mudos_result_t mudos_pipe_write(mudos_pipe_t write_end, const void *buffer, uint64_t size, uint64_t *bytes_written, enum mudos_blocking_mode mode);" and writes as many bytes as can make progress, returning MUDOS_ERROR_BROKEN_PIPE when no reader remains. Syscall 0x0253 is "mudos_result_t mudos_pipe_retain(mudos_pipe_t endpoint, struct mudos_process_handle destination);" and installs one reference/authorization for the same generation-safe endpoint handle in an authorized destination process so the numeric handle may then be transmitted through ordinary IPC. Syscall 0x0254 is "mudos_result_t mudos_pipe_release(mudos_pipe_t endpoint);" and releases one caller-owned endpoint reference; releasing the final writer publishes EOF and releasing the final reader publishes closed-reader state. Syscall range 0x0300 through 0x03FF is reserved for user virtual memory. Syscall 0x0300 is "mudos_result_t mudos_memory_allocate(uint64_t size, uint32_t flags, void **address);" and reserves/maps user virtual memory using the normal MUDOS memory allocator. Ring 3 may request only the user-safe equivalents of MEMORY_USER and MEMORY_ZERO; MEMORY_KERNEL and MEMORY_DMA are never accepted from Ring 3. Allocation size is page-rounded internally as required while the application-visible requested size is validated. Syscall 0x0301 is "void mudos_memory_deallocate(void *address);" and releases a complete allocation created through mudos_memory_allocate or another ABI facility explicitly documented as transferable to this allocator. Syscall 0x0302 is "mudos_result_t mudos_memory_protect(void *address, uint64_t size, uint32_t permissions);" and changes user-page permissions on a validated range while preserving strict W^X, NX and all other kernel security invariants. No call may produce a simultaneously writable and executable mapping. Syscall 0x0303 is "mudos_result_t mudos_memory_query(const void *address, struct mudos_memory_info *info);" and returns safe public metadata about the caller's mapping containing the supplied address, including mapped size, protection and memory priority. It never exposes physical addresses or kernel metadata pointers. Syscall 0x0304 is "mudos_result_t mudos_memory_set_priority(void *address, uint64_t size, uint32_t memory_priority);" and sets the reclaim/paging priority of the caller's mappings to Below_Normal, Normal or Elevated. System_Memory is never user-selectable. Syscall 0x0310 is "mudos_result_t mudos_memory_map_file(struct mudos_entry_handle entry, uint64_t offset, uint64_t size, uint32_t protection, uint32_t map_flags, void **address);" and creates a validated private or shared file-backed Ring-3 mapping using the semantics above. Exactly one of MUDOS_FILE_MAP_PRIVATE or MUDOS_FILE_MAP_SHARED must be selected. Syscall 0x0311 is "mudos_result_t mudos_memory_sync(void *address, uint64_t size, uint32_t sync_flags);" and writes dirty shared file-backed pages in the validated range back through the filesystem; MUDOS_MEMORY_SYNC_DURABLE additionally waits for durable FACIOS/storage completion. It has no writeback effect on anonymous or private-COW pages. Syscall 0x0312 is "mudos_result_t mudos_memory_unmap(void *address);" and unmaps one complete mapping object created by mudos_memory_map_file() or a future ABI facility explicitly documented as compatible; dynamic-module mappings are owned by their module handle and are removed only by mudos_module_unload(). Arbitrary partial unmap is intentionally not part of ABI-v1.1. Syscall 0x0320 is "mudos_result_t mudos_module_load(struct mudos_entry_handle entry, uint32_t flags, mudos_module_t *module);" and validates/maps one .MLIB into the calling process; flags must currently be 0. Syscall 0x0321 is "mudos_result_t mudos_module_find_symbol(mudos_module_t module, const char *utf8_name, uint64_t name_size, struct mudos_module_symbol *symbol);" and returns the type, size and code/data address or module-relative TLS offset for one exported symbol. Syscall 0x0322 is "mudos_result_t mudos_module_tls_address(mudos_module_t module, uint64_t tls_offset, void **address);" and resolves a validated TLS offset to the calling thread's initialized dynamic TLS block for that module, allocating the per-thread block lazily when required. Syscall 0x0323 is "mudos_result_t mudos_module_get_info(mudos_module_t module, struct mudos_module_info *info);" and returns the validated process-local load base, mapped size, file entry, TLS sizing and optional Ring-3 initializer/finalizer addresses. Syscall 0x0324 is "mudos_result_t mudos_module_unload(mudos_module_t module);" and performs the generation-safe unload protocol after the Ring-3 runtime has completed finalization and no dependency/executing-thread constraint prevents removal. Syscall range 0x0400 through 0x04FF is reserved for the VFS, files, directories and volumes. The API never introduces POSIX file descriptors. Stable "struct mudos_entry_handle" values containing volume_id, volume_instance_id, entry_id and entry_generation are used for persistent object references. Syscall 0x0400 is "struct mudos_entry_handle mudos_vfs_root(void);" and returns the shared root directory handle. Syscall 0x0401 is "mudos_result_t mudos_vfs_resolve(const char *utf8_path, uint64_t path_size, struct mudos_entry_handle *entry);" and resolves a validated UTF-8 absolute or ABI-defined path from the VFS according to the caller's permission visibility. Syscall 0x0402 is "mudos_result_t mudos_vfs_lookup(struct mudos_entry_handle directory, const char *utf8_name, uint64_t name_size, struct mudos_entry_handle *entry);" and performs one directory-name lookup without requiring a complete path. Syscall 0x0403 is "mudos_result_t mudos_directory_enumerate(struct mudos_entry_handle directory, uint64_t *cursor, struct mudos_directory_entry *entry);" and iterates readable child entries using a caller-owned opaque enumeration cursor. Cursor value 0 begins an enumeration and MUDOS_ERROR_END reports completion. Entries hidden by FACIOS permission rules are never exposed. Syscall 0x0404 is "mudos_result_t mudos_entry_get_info(struct mudos_entry_handle entry, struct mudos_entry_info *info);" and returns safe public metadata including type, UTF-8 name, size, timestamps, permission tier where applicable and volume association. Syscall 0x0405 is "mudos_result_t mudos_file_create(struct mudos_entry_handle directory, const char *utf8_name, uint64_t name_size, struct mudos_entry_handle *entry);" and creates a new empty file using the existing creator_trust_level, permission_tier and creator_application_id rules. Syscall 0x0406 is "mudos_result_t mudos_directory_create(struct mudos_entry_handle parent, const char *utf8_name, uint64_t name_size, struct mudos_entry_handle *entry);" and creates a directory using the existing immutable directory creator identity rules. Syscall 0x0407 is "mudos_result_t mudos_file_read(struct mudos_entry_handle entry, uint64_t offset, void *buffer, uint64_t size, uint64_t *bytes_read, enum mudos_blocking_mode mode);" and reads from the current visible file-data generation. The non-blocking form returns MUDOS_ERROR_WOULD_BLOCK rather than waiting for storage/decompression. Syscall 0x0408 is "mudos_result_t mudos_file_write(struct mudos_entry_handle entry, uint64_t offset, const void *buffer, uint64_t size, enum mudos_blocking_mode mode);" and performs a normal FACIOS/VFS write subject to the caller's permissions. On FACIOS, success means that the complete replacement state has been accepted into bounded write-batch/recovery resources and published as the latest volatile-visible state; it does not itself guarantee persistence to hardware. Syscall 0x0409 is "mudos_result_t mudos_file_truncate(struct mudos_entry_handle entry, uint64_t new_size, enum mudos_blocking_mode mode);" and changes the logical file size through normal filesystem transactional semantics. Syscall 0x040A is "mudos_result_t mudos_file_flush(struct mudos_entry_handle entry, enum mudos_blocking_mode mode);" and requests an immediate durability barrier for all accepted changes required to make the specified file's currently accepted state durable, including any required predecessor FACIOS transactions. The blocking form returns only after the applicable replacement metadata and required storage flushes have completed successfully or failed. The non-blocking form may begin/promote the durability work but returns MUDOS_ERROR_WOULD_BLOCK if completion is not already available. Syscall 0x040B is "mudos_result_t mudos_entry_rename(struct mudos_entry_handle entry, const char *new_utf8_name, uint64_t name_size);" and renames the entry subject to the existing file/directory ownership and permission checks. Syscall 0x040C is "mudos_result_t mudos_entry_move(struct mudos_entry_handle entry, struct mudos_entry_handle new_parent);" and moves the entry to a new directory while validating every required ownership/permission invariant. Syscall 0x040D is "mudos_result_t mudos_entry_delete(struct mudos_entry_handle entry, uint32_t recursive);" and deletes the entry, where recursive=0 rejects non-empty directory deletion and recursive=1 performs the already specified complete per-entry recursive validation. No .MEXE obtains a permission bypass through this call. Syscall 0x0410 is "mudos_result_t mudos_volume_enumerate(uint64_t *cursor, struct mudos_entry_handle *volume);" and iterates currently mounted volumes. Syscall 0x0411 is "mudos_result_t mudos_volume_get_info(struct mudos_entry_handle volume, struct mudos_volume_info *info);" and returns volume type, filesystem type, total size, available size, block size and other safe public volume information. Syscall range 0x0500 through 0x05FF is reserved for the UI, windowing, input, Unicode text and clipboard. General pixel/shape rendering is not implemented as one syscall per primitive; applications map their own RGBA window surface and draw into it using ordinary Ring 3 code, while text rendering stays integrated with the MUDOS Unicode font engine so shaping, measurement and globally selectable font-engine text remain consistent. Syscall 0x0500 is "mudos_window_t mudos_ui_open_sized(uint32_t window_type, uint32_t width, uint32_t height);" and preserves the existing mudos_ui_open_sized functionality, creating a new program window of the requested validated dimensions. Handle 0 means failure. Syscall 0x0501 is "void mudos_ui_close(mudos_window_t window);" and closes one caller-owned window. Syscall 0x0502 is "mudos_result_t mudos_ui_surface_map(mudos_window_t window, struct mudos_ui_surface *surface);" and maps the caller-owned RGBA drawing surface and returns its address, dimensions and stride through the structure. The application never receives compositor/kernel surfaces belonging to another process. Syscall 0x0503 is "void mudos_ui_surface_unmap(mudos_window_t window);" and releases the caller mapping. Syscall 0x0504 is "mudos_result_t mudos_ui_present(mudos_window_t window, const struct mudos_ui_rect *regions, uint32_t region_count);" and publishes changed regions from the caller's surface into the normal MUDOS UI/compositor invalidation path. A null region array with region_count 0 means the complete window is dirty. The implementation clamps/combines regions into the system's bounded invalidation architecture rather than trusting arbitrary unbounded caller data. Syscall 0x0505 is "mudos_result_t mudos_ui_set_title(mudos_window_t window, const char *utf8_text, uint64_t size);" and changes a caller-owned window title after UTF-8 validation. Syscall 0x0506 is "mudos_result_t mudos_ui_get_size(mudos_window_t window, uint32_t *width, uint32_t *height);" and returns the current client dimensions. Syscall 0x0507 is "mudos_result_t mudos_ui_event_receive(mudos_window_t window, struct mudos_ui_event *event);" and non-blockingly receives the oldest queued event for a caller-owned window. UI events include keyboard press/release, mouse movement, left/right/middle/side-button press/release, mouse wheel, focus gained/lost, window resize, close request and context-menu selection. Input resynchronization from the authoritative keyboard/mouse state is handled internally so applications do not receive permanently stuck logical keys/buttons after queue overflow. Syscall 0x0508 is "void mudos_ui_event_wait(mudos_window_t window);" and returns immediately if the specified window already has a pending event, otherwise blocks until one becomes available or the process/window terminates. Syscall 0x0509 is "mudos_result_t mudos_ui_draw_text(mudos_window_t window, int32_t x, int32_t y, uint32_t pixel_height, uint32_t rgba, const char *utf8_text, uint64_t size);" and sends UTF-8 text to the normal MUDOS Unicode font engine for shaping, fallback glyph selection, rasterization and alpha blending into the caller's window. Syscall 0x050A is "mudos_result_t mudos_ui_measure_text(uint32_t pixel_height, const char *utf8_text, uint64_t size, struct mudos_text_measurement *measurement);" and returns the shaped text dimensions/metrics without modifying a window. Syscall 0x050B is "mudos_result_t mudos_ui_set_context_menu(mudos_window_t window, const struct mudos_context_menu_item *items, uint32_t item_count);" and installs or replaces the caller's context-menu option set for that window. item_count 0 disables the program context menu so right-click performs no application-specific action. Syscall 0x050C is "mudos_result_t mudos_notification_popup(const char *utf8_text, uint64_t size);" and requests the standard global MUDOS Notification Popup containing validated Unicode text. Syscall 0x0520 is "mudos_result_t mudos_clipboard_get_size(uint64_t *utf8_size);" and reports the number of UTF-8 bytes in the current text clipboard. Syscall 0x0521 is "mudos_result_t mudos_clipboard_read_text(char *buffer, uint64_t buffer_size, uint64_t *actual_size);" and copies the current clipboard text into a validated user buffer. Syscall 0x0522 is "mudos_result_t mudos_clipboard_write_text(const char *utf8_text, uint64_t size);" and replaces the global text clipboard after UTF-8 validation. The existing global clipboard limit remains 4 MiB and the clipboard remains text-only. Syscall range 0x0600 through 0x06FF is reserved for audio. Programs deal with signed PCM; WAV, FLAC and other file-format parsing remain outside the raw audio driver/API where already specified. Syscall 0x0600 is "mudos_result_t mudos_audio_get_format(struct mudos_audio_format *format);" and returns the currently selected audio device's active PCM format, including sample rate, sample bit depth/sample representation, channel count and endian ordering. The normal MUDOS output configuration remains little-endian stereo using the highest supported selected-device sampling rate and dynamic range according to the existing audio policy. Syscall 0x0601 is "mudos_audio_stream_t mudos_audio_stream_create(uint32_t direction);" and creates an output or input stream where supported. Syscall 0x0602 is "void mudos_audio_stream_destroy(mudos_audio_stream_t stream);" and closes the stream. Syscall 0x0603 is "mudos_result_t mudos_audio_write(mudos_audio_stream_t stream, const void *pcm, uint64_t frame_count, enum mudos_blocking_mode mode);" and submits complete PCM frames to an output stream. Syscall 0x0604 is "mudos_result_t mudos_audio_read(mudos_audio_stream_t stream, void *pcm, uint64_t frame_count, uint64_t *frames_read, enum mudos_blocking_mode mode);" and receives PCM input frames. Syscall 0x0605 is "mudos_result_t mudos_audio_wait(mudos_audio_stream_t stream, uint32_t events, uint64_t timeout_ns);" and blocks until the selected stream becomes readable/writable or fails. Syscall 0x0606 is "mudos_result_t mudos_audio_set_volume(mudos_audio_stream_t stream, uint32_t volume);" and sets that program stream's mixer volume in the range 0 through 100. Syscall 0x0607 is "mudos_result_t mudos_audio_get_volume(mudos_audio_stream_t stream, uint32_t *volume);" and obtains the current stream volume. Syscall 0x0610 is "mudos_result_t mudos_audio_device_enumerate(uint64_t *cursor, struct mudos_audio_device_info *info);" and iterates available audio devices. Syscall 0x0611 is "mudos_result_t mudos_audio_device_select(uint64_t device_id);" and changes the system-selected device only for ROOT/direct-user-action callers because ordinary applications must not globally reroute system audio without user/system authority. Syscall range 0x0700 through 0x07FF is reserved for time. Syscall 0x0700 is "uint64_t mudos_time_monotonic_ns(void);" and returns MUDOS_64's global monotonic time in nanoseconds using the validated invariant TSC plus per-CPU correction when suitable or the HPET/ACPI PM Timer fallback according to the kernel clocksource rules. It never runs backward. Syscall 0x0701 is "mudos_result_t mudos_time_datetime(struct mudos_datetime *datetime);" and returns the current RTC-derived calendar date/time in the system's defined representation. Ordinary timer delays are implemented using mudos_time_monotonic_ns() and mudos_thread_sleep() rather than exposing numerous separate timer syscalls. Syscall range 0x0800 through 0x08FF is reserved for the native network API. MUDOS_64 does not copy the POSIX/BSD socket API. TLS, HTTP, HTTP/2, WebSocket and other high-level protocols remain userland functionality such as Webby rather than kernel syscalls. Syscall 0x0800 is "mudos_result_t mudos_network_status(struct mudos_network_info *info);" and returns current network availability, selected interface state, local IPv4 information and other safe public status. Syscall 0x0801 is "mudos_result_t mudos_dns_resolve_ipv4(const char *hostname, uint64_t hostname_size, struct mudos_ipv4_address *address, enum mudos_blocking_mode mode);" and resolves one validated hostname through the system DNS resolver. Syscall 0x0810 is "mudos_result_t mudos_tcp_connect(struct mudos_ipv4_address address, uint16_t port, enum mudos_blocking_mode mode, mudos_net_handle_t *connection);" and creates a TCP connection. Syscall 0x0811 is "mudos_result_t mudos_tcp_listen(uint16_t port, mudos_net_handle_t *listener);" and creates a TCP listener where application policy permits listening. Syscall 0x0812 is "mudos_result_t mudos_tcp_accept(mudos_net_handle_t listener, enum mudos_blocking_mode mode, mudos_net_handle_t *connection);" and accepts the next pending connection. Syscall 0x0813 is "mudos_result_t mudos_tcp_send(mudos_net_handle_t connection, const void *buffer, uint64_t size, uint64_t *bytes_sent, enum mudos_blocking_mode mode);" and sends TCP stream bytes. Partial completion is reported through bytes_sent. Syscall 0x0814 is "mudos_result_t mudos_tcp_receive(mudos_net_handle_t connection, void *buffer, uint64_t size, uint64_t *bytes_received, enum mudos_blocking_mode mode);" and receives stream bytes; orderly remote close is reported distinctly from temporary would-block state. Syscall 0x0820 is "mudos_result_t mudos_udp_open(uint16_t local_port, mudos_net_handle_t *socket);" and creates a UDP endpoint. Syscall 0x0821 is "mudos_result_t mudos_udp_send(mudos_net_handle_t socket, struct mudos_ipv4_address destination, uint16_t port, const void *buffer, uint64_t size);" and transmits one UDP datagram. Syscall 0x0822 is "mudos_result_t mudos_udp_receive(mudos_net_handle_t socket, struct mudos_ipv4_address *source, uint16_t *source_port, void *buffer, uint64_t size, uint64_t *bytes_received, enum mudos_blocking_mode mode);" and receives one UDP datagram. Syscall 0x0830 is "mudos_result_t mudos_net_wait(mudos_net_handle_t handle, uint32_t events, uint64_t timeout_ns);" and waits for requested readable, writable, accept-ready, closed or error state without polling. Syscall 0x0831 is "void mudos_net_close(mudos_net_handle_t handle);" and closes a caller-owned TCP/UDP network handle. Syscall range 0x0900 through 0x09FF is reserved for system information, statistics and enumeration. Rather than permanently freezing one syscall for every possible statistic, MUDOS_64 exposes one extensible typed query syscall. Syscall 0x0900 is "mudos_result_t mudos_system_query(uint32_t query, uint64_t index, void *buffer, uint64_t buffer_size, uint64_t *required_size);". Frozen ABI-v1 query IDs initially include MUDOS_QUERY_SYSTEM, MUDOS_QUERY_CPU, MUDOS_QUERY_MEMORY, MUDOS_QUERY_SCHEDULER, MUDOS_QUERY_GPU, MUDOS_QUERY_STORAGE, MUDOS_QUERY_NETWORK and MUDOS_QUERY_AUDIO. Each query has its own versioned output structure whose leading fields contain its structure size/version so additional trailing fields can be introduced compatibly. The query facility supplies statistics required by applications such as Task_Manager, including CPU utilization, physical memory use, virtual memory values, scheduler saturation, memory fragmentation, GPU utilization, storage utilization/fragmentation, process/thread totals, migrations/sec, context switches/sec and scheduling-latency statistics where supported. It exposes no kernel addresses or unsafe internals. Syscall 0x0901 is "mudos_result_t mudos_process_enumerate(uint64_t *cursor, struct mudos_process_handle *process);" and iterates active process identities. Unrestricted enumeration is ROOT/system-management functionality; a normal .MEXE receives only visibility explicitly permitted by policy. Syscall 0x0902 is "mudos_result_t mudos_thread_enumerate(struct mudos_process_handle process, uint64_t *cursor, struct thread_handle *thread);" and iterates threads belonging to an allowed process, with unrestricted foreign-process enumeration reserved for ROOT/system-management callers. Syscall range 0x0A00 through 0x0AFF is reserved for validated privileged ROOT/system-control operations. ROOT remains Ring 3 and does not gain direct access to kernel memory or hardware; these calls merely authorize specific validated kernel operations that ordinary .MEXE programs cannot perform. Syscall 0x0A00 is "mudos_result_t mudos_open_entry(struct mudos_entry_handle entry);" and preserves the existing MUDOS program-opening syscall. It validates the current VFS handle and may launch the referenced .MEXE/.ROOT or open a directory through the appropriate shell mechanism only for ROOT or the kernel-owned direct-user-action path; ordinary .MEXE programs cannot directly launch arbitrary programs through this syscall. Syscall 0x0A01 is "mudos_result_t mudos_process_kill(struct mudos_process_handle process);" and requests normal validated termination of another process. PID 0 cannot be killed through this syscall. Syscall 0x0A02 is "mudos_result_t mudos_process_set_memory_priority(struct mudos_process_handle process, uint32_t priority);" and changes the selected process's user memory priority between Below_Normal, Normal and Elevated. System_Memory is never accepted. Syscall 0x0A03 is "mudos_result_t mudos_system_shutdown(void);" and initiates the complete existing MUDOS shutdown sequence, including rejection of new filesystem modifications, FACIOS durable commit, storage-device flushing, I/O draining, DMA/bus-master shutdown and final power-off. It is restricted to ROOT/system/direct-user-action authority. Syscall 0x0A04 is "mudos_result_t mudos_system_reboot(void);" and performs the equivalent safe durable reboot sequence. Syscall 0x0A05 is "mudos_result_t mudos_register_application_id(struct mudos_entry_handle entry, struct mudos_application_id application_id);" and preserves the existing privileged application-family registration design. It may be called only through the authorized ROOT direct-user-action update path. The kernel computes the executable's complete current SHA-256 itself, stores the supplied registered_application_id together with registered_executable_hash equal to that exact current hash, and the loader uses the registered identity only while the executable's newly computed hash exactly matches the registered hash. Any content-changing replacement clears both registration fields before the changed executable becomes visible. Syscall 0x0A06 is "mudos_result_t mudos_volume_eject(struct mudos_entry_handle volume);" and performs safe unmount/eject of a removable volume through ROOT/direct-user-action authority after normal filesystem and storage synchronization. Syscall 0x0A07 is "mudos_result_t mudos_open_entry_tracked(struct mudos_entry_handle entry, struct mudos_process_handle *process);" and performs the same validated ROOT/direct-user-action program launch as mudos_open_entry() but, when the entry is an executable program, returns the exact newly created child process handle after successful publication. Directory/non-program opening through this tracked call is rejected with MUDOS_ERROR_INVALID_ARGUMENT. This is the normal way for a ROOT launcher that intends to collect an exit status to obtain the child handle without racing process enumeration. The existing mudos_open_entry() remains unchanged for fire-and-forget UI launches. Syscall range 0x0B00 through 0x0BFF is the currently available provisional MUDOS_GPU_API_v0 accelerated graphics/compute extension. These 0x0Bxx calls and the GPU-only types above are intentionally not frozen yet and may change while the GPU extension remains version 0; this exception does not unfreeze any existing non-GPU ABI-major-1 call. Syscall 0x0B00 is "uint32_t mudos_gpu_api_revision(void);" and returns MUDOS_GPU_API_REVISION for the currently implemented provisional GPU extension, or 0 when no GPU API is available. Syscall 0x0B01 is "mudos_result_t mudos_gpu_device_enumerate(uint64_t *cursor, struct mudos_gpu_device_info *info);" and iterates usable accelerated GPU devices, returning MUDOS_ERROR_END after the final device. Syscall 0x0B02 is "mudos_result_t mudos_gpu_device_open(uint32_t device_index, mudos_gpu_device_t *device);" and opens a process-owned GPU context for the selected enumerated device. Syscall 0x0B03 is "void mudos_gpu_device_close(mudos_gpu_device_t device);" and destroys that process-owned context after its resources are safely quiesced/released. Syscall 0x0B04 is "mudos_result_t mudos_gpu_device_wait_idle(mudos_gpu_device_t device, uint64_t timeout_ns);" and blocks with THREAD_BLOCK_GPU until all previously submitted work on that process-owned device context has completed, failed or timed out; UINT64_MAX means no timeout. Syscall 0x0B10 is "mudos_result_t mudos_gpu_buffer_create(mudos_gpu_device_t device, const struct mudos_gpu_buffer_desc *desc, mudos_gpu_buffer_t *buffer);" and creates a validated process-owned GPU buffer. Syscall 0x0B11 is "void mudos_gpu_buffer_destroy(mudos_gpu_buffer_t buffer);" and destroys a buffer only after no outstanding command submission may still access it. MUDOS_FEATURE_GPU_ACCELERATION is reported only when at least one usable device implements this provisional GPU extension. Syscall range 0x0C00 through 0x0CFF is reserved for future device APIs. Syscall range 0x0D00 through 0x0DFF is reserved for future debugging and profiling functionality. Syscall range 0x0E00 through 0x0EFF is reserved for future virtualization functionality. Syscall range 0x0F00 through 0x0FFF remains unassigned and reserved for future ABI-v1 expansion. The frozen MUDOS_API_ABI_v1.1 therefore exposes the operating-system primitives required by ordinary applications and trusted ROOT system utilities: ABI discovery, secure randomness, process/thread management with exit-status waiting, native Ring-3 TLS/TSS, synchronization, IPC/shared pages, byte-stream pipes, wait-many/completion queues, anonymous and file-backed user virtual memory, dynamically loadable Ring-3 .MLIB modules, VFS/file/directory/volume operations, window surfaces, input events, Unicode text, clipboard, PCM audio, time, networking, system information and a small explicit privileged ROOT control set, while MUDOS_GPU_API_v0 additionally exposes immediately usable accelerated graphics, compute, GPU resources, SPIR-V shaders, pipelines, command submission, synchronization and window presentation as a deliberately provisional extension. High-level application functionality such as C libraries, Python modules, image codecs, WAV/FLAC parsing, HTTP, network TLS, browser engines, widget libraries, paint primitives, language runtimes and compiler support are implemented in Ring 3 programs or dynamically loadable .MLIB libraries on top of these primitives rather than each becoming its own kernel syscall; "network TLS" here means Transport Layer Security and is distinct from the native thread-local-storage TLS facility. Existing non-GPU syscall IDs, signatures and semantics above are frozen for ABI major version 1. Syscalls 0x0B00 through 0x0BFF and the GPU-only types/semantics explicitly marked MUDOS_GPU_API_v0 are the sole current exception and may change until that GPU extension is explicitly frozen. Future MUDOS_64 releases may add previously unused non-GPU syscall IDs, new feature bits, new query IDs and new versioned structures while remaining ABI-v1 compatible, but may not alter the existing frozen non-GPU ABI-v1 contract. The Wi-Fi and Bluetooth drivers currently target AX200, AX201, AX210 and AX211 (Intel only intentionally for now). The Intel GPU driver supports Intel integrated graphics down to Intel 10th gen up to the newest Intel CPU integrated GPU only (not Intel dedicated GPUs).
